# The skills: what to build, and what to measure before building it

*2026-09-17. A plan, not a build. Nothing here is installed yet.*

**None of this is the current work, and the order below says so.** Four documents
of 346 are read. The next thing that happens is the fifth, by hand, with a
candidate list written while reading — because there are still **zero** usable
gold examples and every skill here would otherwise be scored against nothing.

That matters most for the two phases that look like the interesting ones.
`qmd bench` and `model-here` are **continuous-optimization instruments**: they
answer „is this getting better" and they need a baseline and a held-out set to
answer it at all. Building them now would produce a number with no denominator,
which is the exact failure this project keeps writing down. They are in the plan
because a continuous loop needs them *eventually* and because building them
later, under pressure, produces the version that flatters itself.

So: read the documents. The instruments wait.

Two jobs were asked for. **One set of skills carries the workflow** — the steps a
person or an agent walks to turn a Drive export into a wiki page. **Another set
makes the tools reliable** — qmd and DSPy are both easy to invoke and easy to
invoke wrongly, and neither says so when it happens.

They are different in kind. A workflow skill encodes *what this project does*. A
tool skill encodes *what this project learned about a tool that the tool's own
documentation does not say*. If a tool skill only repeats the `--help` output, it
should not exist.

## Phase 0 — ground both tools, because the plan below is currently a guess

Two things were found by reading the installed package rather than the docs, and
both change what a skill would say.

### `qmd bench` is a full IR evaluation harness and we have never run it

```
qmd bench <fixture.json> [--json] [-c collection]
```

It runs every query through **four backends** — `bm25`, `vector`, `hybrid`,
`full` — and reports `precision@k`, `recall`, `recall@1`, `recall@3`,
`recall@5`, `mrr`, `f1` and `latency_ms` for each, plus the expected files it
missed. The fixture is small:

```json
{ "description": "...", "version": 1, "collection": "sources",
  "queries": [{ "id": "...", "query": "...",
                "type": "exact|semantic|topical|cross-domain|alias",
                "description": "...", "expected_files": ["..."],
                "expected_in_top_k": 1 }] }
```

**A skill that tells an agent which backend to use, without this, is inventing
its recommendation.** `CLAUDE.md` said qmd „answers a lowercase German phrase in
about 0.2s" and recommended structured `lex:`/`vec:`/`hyde:` queries over pasting
the question. **Both halves were wrong, and measuring them was the first useful
thing this plan produced.**

| claim | measured |
|---|---|
| „about 0.2s" | `search` 0.24s, `query` **14.5s** on a query never asked, twice. The 0.2s came from the index's `llm_cache`: the documented example phrase had been asked before. No GPU in this container; qmd says so. |
| write `vec:` and `hyde:` lines | **0 of 464 documents are embedded.** `vsearch` returns „No results found". Every qmd result this project has ever used came from BM25 alone, and a `vec:` line contributes nothing until `qmd embed` runs. |
| `qmd bench` would settle the backends | It would measure the absence of embeddings. `vector` and `full` score near zero by construction. **`qmd embed` comes first, and it is not free** — 464 documents on CPU. |

So phase 0b grew a prerequisite it did not have, and the advice in `CLAUDE.md`
was corrected rather than tested.

**And the fixture is already written, for another reason.** Every
`Wiki/questions/` page, every conflict record and several notes contain a
sentence of the form „a search across all 346 landed documents finds this, in
`<slug>`" — a query and its expected file. `Wiki/conflicts/c4` and
`Wiki/questions/q1` each carry one with a line number. That is the same accident
as the judgement ledger turning out to be a trainset: **the labels exist because
the work produced them, not because anyone set out to build an evaluation set.**

So Phase 0 is: harvest those claims into `Plan/runs/qmd-bench.json`, run it, and
let the numbers decide what the skill says. Expected cost: an hour, no model.

The `alias` and `cross-domain` query types are the interesting ones here — a
corpus where `Kern-Welt`, `Kern-Welten` and `Die Konstrukt-Stadt` are the same
subject is exactly what those categories are for.

### Built 2026-09-17: the `decisions` collection

Not one of the phases below — it was cheap, it was asked for, and it paid for
itself immediately. **A collection spanning the reconciliation records, conflict
records, question pages, `Plan/decisions/` and the judgement ledger**, excluded
from default queries and asked by name: *what has already been decided, and why?*

Measured on its first query: `Wächter` returns three hits — the Q4 page, `J20` in
the ledger at line 273, and the reconcile record at line 68 — and
`qmd get <ref>:273:12` then reads twelve lines. The eight reconciliation records
are 953 lines and were previously read whole.

**It needed one thing built first, and that is the finding.** qmd indexes
`**/*.md` and nothing else — 1,047 files in the index, every one markdown, zero
JSON. So `judgements.jsonl` and every `reconcile.json` were invisible to every
search, which is precisely backwards: they are the densest record of what was
decided and the thing most worth finding without re-reading. `judgements.py` now
writes a rendered `Plan/runs/judgements.md` on every run, so it cannot lag behind
the ledger it derives from.

The same treatment is available for `reconcile.json` and is **not** being applied
yet: its prose counterpart in `Wiki/compare/` already carries the same decisions,
and rendering both would put two searchable copies of one decision in one
collection. That changes the moment a field exists in the JSON and not in the
prose.

`setup_qmd.sh --check` reported „7 of 6" when the collection was added, because
it carried the number 6 as a constant. Derived now — the same defect as the
three-file list in `--prose`, one directory over.

### Three qmd surfaces we are not using at all

| surface | what it is | why it might matter |
|---|---|---|
| ~~`qmd mcp`~~ | **decided: no.** An MCP server over stdio, exposing four tools — `query`, `get`, `multi_get`, `status` | Dropped on the author's call: the CLI is enough, and a skill that documents every step is clearer written against commands a person can also type. MCP would also hide the four things it does not expose — `collection`, `context`, `embed`, `bench` — behind a surface that looks complete |
| `qmd context add` | human-written summaries attached to a collection | **Measured: the context never reaches the reranking model.** It is stored per collection, attached to results as metadata and printed above `get` output. It is documentation for a reader, not an input to search — which is still useful, and is not what „context" suggests |
| `qmd skills list` | the package ships `qmd` **and** `release` | We installed one and never looked at the list |

`qmd mcp` is now decided against, for a reason worth keeping: **a skill whose job
is to describe every step should name commands, not tool calls.** A reader can
type a command, check its output and disagree with it; an MCP tool call is
invisible in exactly the way this project's process artifacts exist to prevent.
`scripts/qmd.py` stays as the Python handoff.

### DSPy: the reliability problem is not the API

33 `dspy-*` skills are installed. They teach the API well and the repo
`netzkontrast/dspy-agent-skills` keeps them checked against 3.3.x. **Nothing
there knows anything about this corpus**, and every failure this project has had
with a model was a *methodology* failure, not an API one:

- a model that **tied the baseline's score while merging `Negentropie` with
  `Entropie`** — 14/17 either way, and one of them destroys the distinction the
  whole wiki rests on. Caught only because a held-out canary existed.
- an RLM that reproduced the document's **own off-by-one** („vier" where five are
  named), which looks like a correct answer.
- `94% vs 82%` on 17 items being `16 vs 14`, with no held-out split.

So the DSPy skill this project needs is **not** a DSPy skill. It is a rule about
what must be true before a model's output is allowed into `Sources/` or `Wiki/`.

## The skills

Five. Each carries the three lines `CLAUDE.md` requires of a provisional
construct — what it may not do, and what would retire it.

### 1. `account` — the workflow, as one verb

```yaml
name: account          # provisional
# may not: decide a conflict, promote a page, or write a number it did not measure
# retire when: a person reaches for the step scripts directly three times running
```

`CLAUDE.md` is explicit that **a pipeline of N steps needs N rule sets, N formats
and N learnings files, and grows forever.** So this is not five skills named
`census`, `read`, `reconcile`, `gather`, `ask`. It is one skill over
`account(subject, question)`, dispatching on the subject:

| subject | what the skill walks |
|---|---|
| a document | profile → briefing → census → note, with `capture.py` refusing to count before a candidate list exists |
| a term | the page, readings attributed and unmerged |
| two surfaces | `fold()` first, then a judgement recorded in the ledger |
| the corpus | a count from `corpus.py` / `duplicates.py`, never a qmd result |

The thing a skill adds over the scripts is **order and refusal** — that the
census is frozen before the wiki is consulted, that a candidate list is written
while reading and not reconstructed afterwards, that a quotation is checked. All
three have been violated at least once, and each violation was caught late.

### 2. `land` — fetching, which is genuinely a different operation

```yaml
name: land              # provisional
# may not: open a spill file, read a document's bytes, or re-fetch a folded drive_id
# retire when: fetching is finished — 271 rows remain
```

Small, and worth separating for one reason: **no model reads the bytes.** The
`read_file_content` call reports a path in what looks like an error, and that is
the good path; `sources.py land --consume` parses it. An agent that "helpfully"
opens the spill has broken the one property this step has. That mistake is
cheap to make and invisible afterwards.

### 3. `checks` — run the battery, and say what a red one means

```yaml
name: checks            # provisional
# may not: fix what it finds, or call a failure a flake
# retire when: the checks run in CI instead
```

Seven commands exist and their *failure meanings* live in `CLAUDE.md` prose:

```
account.py order      the pipeline's dependency order
state.py --prose      every number written anywhere, over every .md
judgements.py         DISAGREES means go and look
quotes.py             unresolved vs. unchecked, never conflated
duplicates.py         files and documents must stay the same number
qmd_coverage.py       a file in no collection is silently unsearchable
sources.py check      manifest against disk, both directions
```

The value is in the second column. `judgements.py` replaying green **says the
recorded decisions still hold, not that the code around them is right** — that
sentence was bought with a bug that created six pages for three worlds, and it
belongs where someone reads it before trusting a green run.

### 4. `qmd-here` — how to search *this* corpus

```yaml
name: qmd-here          # provisional
# may not: let a search result become a number in a page or a learning
# retire when: Phase 0 shows the backends are indistinguishable on this corpus
```

**Blocked on Phase 0.** What it will carry, once measured:

- which backend answers which of the five query types, from the bench table —
  now actually runnable: the embedding model is `embeddinggemma-300M-Q8_0`,
  **qmd's own default and the small one**, ~300 MB against Qwen3-Embedding-0.6B's
  ~640 MB. It was never downloaded, which is why 0 of 465 documents were
  embedded; `qmd pull` fetched it and `qmd embed` is filling the index
- whether structured `lex:`/`vec:`/`hyde:` queries actually beat a plain phrase
  here, or whether that advice was reasoning rather than measurement
- that **a `Hit` says where to look and carries no claim about the corpus** —
  `hit.document()` is the handoff back to the tools that count
- the failure that has no error message: a collection that does not cover a
  directory, and `setup_qmd.sh --check` as the response
- `--mask`, not `--pattern`, which is ignored and cost a 1,382-file collection

The bundled `qmd` skill stays installed and is not replaced. It teaches the tool;
this teaches the corpus.

### 5. `model-here` — what must be true before a model's output is used

```yaml
name: model-here        # provisional
# may not: name a model, a provider or a price — those change
# retire when: three optimized programs have shipped under it without incident
```

Not a DSPy skill. Five rules, each bought:

1. **Baseline first, and it is usually `fold()`.** 14/17 = 82% is the number to
   beat, and it was never written down until a model was already running.
2. **A held-out canary that the training set cannot teach.**
   `Negentropie`/`Entropie` paid for itself on its first run.
3. **A score is a fraction with a denominator.** 94% against 82% on 17 items is
   16 against 14.
4. **Every dependency into `.venv-tools`.** `--break-system-packages` took the
   container's interpreter down with `cryptography`.
5. **Free models only**, and the key lives in a git-ignored `.env`.

Rule 2 is the one worth arguing for: it is what separates a model that is better
from a model that scores the same while destroying a distinction.

## Order

| | what | needs | gate |
|---|---|---|---|
| — | **read documents 5, 6, 7 by hand** | nothing | *this is the current work* |
| 1 | `checks` | nothing | none — needs no measurement |
| 2 | `account`, `land` | 1 | each step done by hand twice more |
| 0a | harvest `Plan/runs/qmd-bench.json` from existing wiki claims | nothing | cheap enough to do opportunistically |
| 0b | `qmd bench` over four backends | 0a | **not until search is the bottleneck** |
| 0c | the three unused surfaces — `mcp`, `context`, `skills list` | nothing | only if a subagent needs search |
| 3 | `qmd-here` | 0b | |
| 4 | `model-here` | a second trainset and a held-out split | **not until there is something to optimize** |

**Phase 1 first and deliberately.** `checks` needs no measurement, is the
smallest, and is the one that catches a mistake made by any of the others. Every
other skill here can produce a wrong wiki page; `checks` is what notices.

**Phases 0b and 4 are gated on need, not on order.** A benchmark answers a
question nobody is asking yet: search is not currently what makes this slow —
reading is. When a document takes an hour and forty minutes of it is finding
things, 0b becomes urgent and not before.

## What this plan is not allowed to become

`CLAUDE.md` says a description that outruns what exists is how the previous
version of this project failed. Five skills for a project with **four documents
read** is already close to that line. The mitigation is the `retire when` on each
and the order above: nothing in Phase 2 or later gets written until the thing it
is a skill *for* has been done by hand at least twice.
