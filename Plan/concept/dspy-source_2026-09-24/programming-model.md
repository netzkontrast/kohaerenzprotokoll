**What this part of DSPy is, in 5 lines**: `dspy/signatures/` is the typed prompt contract (fields, instructions, string-vs-class parsing) that every module compiles against. `dspy/primitives/` is the data model — `Example` (input data), `Prediction` (output data, an `Example` subclass with completions and arithmetic), `Module`/`BaseModule` (the composition unit: tree-walk, deepcopy, save/load). `dspy/core/types.py` is a large, mostly-internal typed request/response/streaming protocol (`LMRequest`/`LMResponse`/`LMMessage`/`LMPart`) that is the foundation of a new, not-yet-default `forward_contract = "typed_lm"` calling convention for `BaseLM` subclasses. `dspy/dsp/utils/settings.py` is the `dspy.configure`/`dspy.context` singleton, a global dict plus a `contextvars`-based override stack. The `utils/` files in scope are small, independent infrastructure: a vendored `magicattr` (dotted/bracket path get/set), a lazy-import shim for optional deps, the `@experimental` docstring-only marker, and `DummyLM`/`dummy_rm`, DSPy's own offline-testing fixtures.

## 2. Knowledge items

### API

- **`Signature("...")` never returns an instance** — the metaclass `SignatureMeta.__call__` intercepts any call where `cls is Signature` and routes it through `make_signature(...)`, returning a new **class**, not an instance. `Signature("a -> b")(a="x", b="y")` (instantiating the returned class) does work and gives a real pydantic `BaseModel` instance — string form and class form both end at the same kind of object, a `Signature` subclass. `dspy/signatures/signature.py:41-51,271`. [api] (verified: read + probe `custom-type-frame-detection-signature-only`) · skill: **same** (api.md shows both spellings but doesn't explain the metaclass mechanics or that instantiation works)

- **`Signature("field: MyType -> ...")` auto-detects a custom type from the caller's stack frame — but only when called as `Signature(...)`, never through `make_signature(...)` directly.** `SignatureMeta.__call__` calls `_detect_custom_types_from_caller(args[0])` only when `custom_types` is `None` and `args[0]` is a string; it walks up to **100 frames**, checking each frame's `f_locals` then `f_globals` for the bare name, and logs a warning naming the 100-frame bound if it can't finish. Calling `dspy.signatures.signature.make_signature(...)` directly with no `custom_types=` does **not** do this walk and raises `ValueError: Unknown name: ...`. `dspy/signatures/signature.py:41-51,53-136`. - **A string signature can embed `Annotated[T, Field(...)]`, including a real pydantic `Field(...)` call — but it silently loses the metadata and never reaches the prompt.** `_parse_type_node` parses field strings via `ast.parse(f"def f({field_string}): pass")` and specifically handles an `ast.Call` node whose function name is literally `"Field"` (`signature.py:805-813`), constructing a real `pydantic.Field(**kwargs)` from the AST keywords. So `dspy.Signature("score: Annotated[int, Field(ge=0, le=10)] -> label: str")` parses without error. But: `sig.input_fields["score"].annotation` comes back as plain `int` — the `Annotated` wrapper and its embedded `Field(...)` are gone by the time the class is built (pydantic absorbs/merges Annotated-embedded `Field` metadata into the constructed `FieldInfo`, collapsing the annotation) — and `json_schema_extra` has **no** `"constraints"` key. Contrast with `OutputField(ge=0, le=10)` (an ordinary kwarg on `InputField`/`OutputField`), which *does* produce `json_schema_extra["constraints"] = "greater than or equal to: 0, less than or equal to: 10"` via `field.py`'s `PYDANTIC_CONSTRAINT_MAP` (`field.py:27-36,55-58`) — this is the string the adapter puts in the prompt. `dspy/signatures/field.py:39-59`; `tests/signatures/test_signature.py:427-442` is DSPy's own test for the `InputField(ge=..., le=...)` path. [api][trap] (verified: ran `string-signature-annotated-field-constraint`, then a follow-up probe confirming `annotation == int`, `__metadata__ is None`, no `constraints` key) · skill: **new**

- **Numeric/length constraints on a field reach the prompt only through `InputField`/`OutputField` kwargs, never through the type annotation.** Any pydantic constraint kwarg not in DSPy's own arg list (`desc`, `prefix`, `format`, `parser`, the internal `__dspy_field_type`/`IS_TYPE_UNDEFINED`) is passed straight to `pydantic.Field(**kwargs)` *and* separately stringified into `json_schema_extra["constraints"]` if it's one of `gt/ge/lt/le/min_length/max_length/multiple_of/allow_inf_nan` (`field.py:27-70`). `desc=` falls back to a plain pydantic `description=` kwarg if `desc` itself isn't given (`field.py:52-54`) — so `OutputField(description="...")` also works. `dspy/signatures/field.py:39-70`. - **`Signature.dump_state()`/`load_state(state)` save only `instructions` and, per field, `prefix`/`desc` — never field names or types — and `load_state` re-applies them onto the *live* target Signature's fields **positionally, by `zip`, not by name**.** `state = {"instructions": ..., "fields": [{"prefix":..., "description":...}, ...]}`; `load_state` does `zip(signature_copy.fields.values(), state["fields"], strict=False)` (`signature.py:523-545`). If the target signature has fields in a **different order** than the one the state was dumped from (same names, reordered — e.g. after an `insert`/`prepend`), the wrong `prefix`/`desc` lands on the wrong field, silently (non-strict zip also silently truncates on a length mismatch). def load_state(self, state, *, allow_unsafe_lm_state=False):
```python
    from dspy import Module
    def _apply(module):
        for name, param in module.named_parameters():
            if isinstance(param, Module):
                param.load_state(state[name], allow_unsafe_lm_state=allow_unsafe_lm_state)
            else:
                param.load_state(state[name])
    _apply(self.deepcopy())  # trial run raises before self is touched
    _apply(self)
```

```python
def probe_forward_direct_call_warns():
    import dspy, logging
    class M(dspy.Module):
        def forward(self, x):
            return x
    m = M()
    logs = []
    class H(logging.Handler):
        def emit(self, record):
            logs.append(record.getMessage())
    h = H()
    logging.getLogger("dspy").addHandler(h)
    try:
        m.forward("t")
        direct = any("directly is discouraged" in x for x in logs)
        logs.clear()
        m(x="t")
        via_call = any("directly is discouraged" in x for x in logs)
    finally:
        logging.getLogger("dspy").removeHandler(h)
    if direct and not via_call:
        return None
```

## 6. Ten things the skill must say

1. **`dspy.Signature("field: MyType -> ...")` resolves a custom type by walking up to 100 caller stack frames automatically — `make_signature(...)` called directly does not.** api.md currently says the opposite ("A custom type in a *string* signature needs `make_signature(..., custom_types={...})`"), and this repo's `pairs.py` uses string signatures.
2. **`Module.load_state` is transactional**: it dry-runs the whole state application against `self.deepcopy()` first and only commits to the live module if that succeeds (DSPy's own regression test, GH-9589). Any state-mutating step this repo adds to `pairs.py`/optimizer work should copy this shape rather than mutate in place and hope.
3. **`Signature.load_state` matches saved field metadata to the target's fields *by position*, not by name** — safe only when the reloaded signature has the same field order it was dumped with.
4. **JSON-loaded `predictor.demos` are plain dicts; `.pkl`-loaded ones remain real `Example` objects** — code that calls `.inputs()`/`.q` on a demo after `Module.load("x.json")` will fail in a way it won't after `Module.load("x.pkl", allow_pickle=True)`.
5. **`Module.save`/`load` has three modes, not two**: `.json` (state, human-readable), `.pkl` with no `save_program` (state-only, pickled — for state that doesn't survive JSON), and `save_program=True` (a *directory* with `program.pkl` + a separate `metadata.json`).
6. **`dspy.RLM` (and `GEPA`'s internals, `ReActV2`, `Flex`) are marked `@experimental`** — a docstring-only, zero-runtime-effect marker, but a real upstream-stability signal for `rlm_ingest.py`'s foundation that nothing in the skill currently flags.
7. **A plain `threading.Thread`/bare `ThreadPoolExecutor` does not inherit a `dspy.context(...)` override** — only `dspy.Parallel`, `Module.batch`, `asyncify`, and native `asyncio` propagation do. Anything in this repo that hand-rolls threads around a DSPy call needs to re-`dspy.context(...)` inside the worker.
8. **`Module.__getattribute__` warns on any direct access to `.forward` outside `__call__`, and pays an `inspect.stack()` cost every time** — call modules as `module(...)`, never `module.forward(...)`, including via `hasattr`/bound-method references.
9. **`Example.__hash__` raises `TypeError` on any field holding a list/dict** (e.g. `image_list=[...]`), and `Example.__setattr__` silently shadows a field name that collides with a method name (`ex.get = ...`, `ex.items = ...`) — both are silent-until-they-aren't failure modes for code that builds `Example`s from arbitrary column names.
10. **`dspy.core` (`dspy.LMRequest`/`LMResponse`/`LMConfig`, and the `System`/`User`/`Assistant`/`ToolResult` builders) is a whole typed layer the skill doesn't mention at all** — currently dead weight for this repo (nothing here uses `forward_contract = "typed_lm"`), but it's what `lm_fixture.py`/`claude_lm.py` would need to target if DSPy ever defaults `dspy.LM` to it, and `LMResponse.from_text(...)` is already a drop-in nicer constructor than the hand-rolled `SimpleNamespace` both scripts build today.
