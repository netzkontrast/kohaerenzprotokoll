# Scan: `/home/user/dspy-optimizer`

## 1. What it is

A small, generic library (not an app) implementing an **Evaluator → Refiner →
Validator → Merger** loop that iteratively patches a text prompt against a
labelled dataset until it passes (or `max_refine_iters` is exhausted). Targets
DSPy `>=2.6.27` in `pyproject.toml`, but `uv.lock` pins exactly `2.6.27`; the
code itself is API-thin enough that it also runs unmodified under DSPy 3.3.1
(verified below). Maturity: **well-tested, never run for real** — 43 unit/
integration tests, all against a hand-rolled `MockLLM`, no live LLM run in the
repo, and the flagship example (`examples/dutch_invoices/`) that README.md and
DESIGN.md both describe **does not exist on disk** (confirmed: only
`DESIGN.md`, `LICENSE`, `README.md`, `dspy_optimizer/`, `tests/`,
`pyproject.toml`, `uv.lock` are present). Treat the invoice framing as
documentation of intent, not as code to read.

## 2. Every good idea

1. **Registry with decorator + string lookup** (`dspy_optimizer/strategies/registry.py:6-34`) — a tiny `Registry` class (`register(name)` decorator, `get(name)`) used identically for mergers/validators/scorers. `[adapt]` — kohaerenzprotokoll's `scripts/rules/` decomposition library could use exactly this pattern to let `account.py` pick a strategy by name instead of importing concretely.
2. **String-or-callable strategy selection** (`optimizer.py:69-76`) — `scorer` can be a registered name or a raw function; unknown name raises `ValueError` naming the missing key. `[adapt]` — cheap, readable API surface; useful anywhere kohaerenzprotokoll exposes a `--strategy` CLI flag (e.g. a future `judgements.py --rule <name>`).
3. **`with_instructions` for thread-safe dynamic prompting** (`evaluator.py:36-43`) — instead of mutating a shared `dspy.Signature`, it clones one per call via the official immutable API, so parallel evaluation cannot race on prompt text. `[adopt]` — directly relevant the moment kohaerenzprotokoll parallelizes any DSPy call (e.g. batched one-term-or-two judgements); avoids a real, easy-to-hit bug class.
4. **Frozen dataclasses for config/patch objects** (`models.py:7-45`) — `Config` and `PromptPatch` are `@dataclass(frozen=True)`; tests assert `AttributeError` on mutation (`tests/dspy_optimizer/test_models.py:42-50`). `[adopt]` — matches the target's existing taste for immutable, inspectable records (e.g. `judgements.jsonl` rows) and is free to copy.
5. **Enum for a small closed operation set** (`models.py:22-27`, `PatchOperation.APPEND/REPLACE`) — avoids magic strings for the one place the code branches on operation type. `[adopt]` — small, safe pattern for e.g. a future `fold()` decision enum (`same_term` / `different_term` / `unclear`).
6. **Block-based, regex-anchored prompt merging** (`strategies/merger/block_based.py:18-59`) — finds a `### Block Name` header with `re.escape` + `MULTILINE`, appends/replaces up to the next `###` header or EOF, raises `ValueError` naming the missing block rather than silently no-op'ing. `[adapt]` — this is a merger of **prompt text sections**, never of two documents' factual claims; safe pattern to imitate for e.g. programmatically composing a `SKILL.md` from named blocks (job 4, skill descriptions), but not applicable to combining two sources' *readings* (see §4).
7. **Named-block prompt convention itself** (`### Task / ### Output Format / ### Examples / ### Heuristics`, `README.md:28-29`, `refiner/signature.py:18-27`) — a documented convention that keeps a growing prompt both machine-patchable and human-readable. `[catalogue]` — worth keeping as a possible prompt-authoring convention for kohaerenzprotokoll's own DSPy signatures (e.g. `rlm_ingest.py`), not urgent.
8. **Explicit "unreachable" branch documented as such** (`block_based.py:55-57`) — `else: raise ValueError(f"Unsupported operation: {patch.operation}")` with a comment noting it should be impossible given the enum. `[adopt]` — small defensive-programming habit; matches P23 (guard reports what it could not check) in spirit even though it's a different guard.
9. **`FullValidationStrategy` fails fast** (`strategies/validation/full.py:40-60`) — returns `False` the instant one example in the validation set fails, rather than scoring the whole set and thresholding. `[catalogue]` — useful default when "no regressions" must mean *zero* regressions (matches P13's spirit of never silently degrading an already-correct case), but wrong shape for kohaerenzprotokoll's actual metric needs (see #10, #20).
10. **`SampleValidationStrategy` with configurable threshold** (`strategies/validation/sample.py:12-74`) — unlike `full`/`batched`, it computes a **fractional score** over a sample and compares to a `threshold` (default 1.0), returning `{"is_valid": bool, "score": float}` instead of a bare bool. `[adapt]` — this is the one strategy with headroom below 100%; relevant if kohaerenzprotokoll ever wants "accept if ≥90% of the labelled surface-pairs still resolve" instead of all-or-nothing.
11. **Validator return-type polymorphism handled at the caller** (`optimizer.py:163-169`) — the main loop accepts either a bare `bool` or a `{"is_valid", "score"}` dict from any validator and normalizes it. `[adapt]` — lets you swap a threshold-based validator in later without touching the orchestrator; a decent shape for a strategy interface that started strict and grew.
12. **Registered, pluggable scorers with a strict "no output field → False" contract** (`strategies/scoring/common.py:26-33`, `64-72`) — `exact_match_scorer`/`numeric_scorer` both return `False` (never raise, never silently pass) when there is no output field or a parse error, rather than crashing the whole optimize loop on one malformed example. `[adopt]` — fail-closed default is exactly the shape P19 (assert non-empty) wants; but note the empty-dataset case elsewhere is fail-*open* (see §4, item 2) — inconsistent within the same repo.
13. **Numeric scorer normalizes European vs. thousands-separator number formats** (`common.py:76-84`) — strips thousands commas, then treats any remaining comma as a decimal comma, before `math.isclose(rel_tol=...)`. `[adapt]` — directly reusable idea (not code, since the domain differs) for any future German-number-format scorer, e.g. checking whether a candidate reading in a note transcribes a percentage or a date the same way source and page do.
14. **Every scorer is unit-tested for both the happy path and the malformed-input path** (`tests/.../test_common_scorers.py:22-27,63-69`) — e.g. `test_numeric_scorer_invalid_string` asserts `False` rather than an exception. `[adopt]` — good test-writing discipline: always pair a "works" test with a "garbage input degrades safely" test, which is exactly the selftest.py philosophy in kohaerenzprotokoll (P23).
15. **Self-critique loop carries an explicit failure history into the next attempt** (`optimizer.py:106,184-187`; `refiner/signature.py:39-41`) — each refinement receives a stringified list of "Failed Attempt N: Operation…Target…Content…" so the LLM does not repeat a rejected patch. `[adapt]` — same idea as kohaerenzprotokoll's own "history of previously failed suggestions" instinct; could inform a future `judgements.py`-driven refiner that must not re-propose a decision a human already rejected for the same surface pair.
16. **Few-shot exemplars embedded directly in the `dspy.Signature` docstring** (`refiner/signature.py:6-108`) — two fully worked "Example 1 / Example 2" cases (with Analysis → Suggestion → Target Block → Operation → Content) live inside the Signature's docstring, which DSPy renders as system instructions. `[catalogue]` — plausible technique for a `one-term-or-two` DSPy signature carrying 2-3 of the 26 labelled `surface-pairs.jsonl` rules as worked examples, though `dspy.Example`-based few-shot (via `LabeledFewShot`) is the more idiomatic DSPy mechanism and is already on the target's roadmap.
17. **Callback protocol with a full lifecycle** (`callback/base.py:16-46`) — `on_run_start/end`, `on_refinement_start/end`, `on_validation_start/end`, `on_merge_success/failure`, each passed a mutable `state` dict. `[adapt]` — clean audit-hook shape; would let kohaerenzprotokoll add a `--trace` mode to any DSPy call site (job 3's `rlm_ingest.py`, job 1's fold-optimizer) by writing one callback class instead of instrumenting the loop body.
18. **`HistoryCallback` as the offline, dependency-free audit trail** (`callback/history_callback.py:20-27`) — appends `{"event": name, **state}` to an in-memory list on every lifecycle hook; no external service, no network. `[adopt]` — this is the closest thing in the repo to the target's planned `--trace` mode: it is literally "log every step of a DSPy loop to a Python list/JSON with zero dependencies." Needs adaptation: `state` holds live `dspy.Example`/`dspy.Prediction` objects, not JSON-serializable — would need a `to_dict()`/redaction pass before writing to disk (German-text-safe).
19. **`MLflowCallback` is optional and fails loud, not silent, when missing** (`callback/mlflow_callback.py:8-14, 42-46`) — `import mlflow` is wrapped in `try/except ImportError`, and the callback class itself raises `ImportError` with an actionable message only when *instantiated*, not at import time of the package. `[adopt]` — nice pattern for optional heavy deps (mirrors how kohaerenzprotokoll treats `.venv-dspytools`/`.venv-typesafe` as optional, rebuildable venvs); the "fail at construction, not at import" detail avoids breaking every other test/tool that imports the `callback` package.
20. **MLflow logs a `validation_score` and a `patch` (target block + op + content) per step**, not tokens/cost (`mlflow_callback.py:82-113`) — confirms there is **no cost/token accounting anywhere in the repo** (see §4). `[catalogue]` — the idea of tagging every merge with the exact patch text and target block, indexed by `total_evaluations` as the MLflow "step", is reusable for a lightweight trace log even without MLflow itself.
21. **`MockLLM` conforms to `dspy.BaseLM` and returns a synthetic OpenAI-shaped response with `_hidden_params.response_cost=0.0`** (`tests/conftest.py:9-53`) — a genuinely correct, minimal way to unit-test DSPy modules with zero network calls; discovered by testing (comment says "as expected by `_process_lm_response`"), i.e. someone read DSPy internals to make this work. `[adopt]` — this is the single most reusable artifact in the repo for kohaerenzprotokoll's P5 ("every workflow ships an offline, no-key fixture"): it is a ready-made, DSPy-version-compatible mock LM that can back a fixture for job 1/3/4's future DSPy signatures. Verified working under both DSPy 2.6.27 and 3.3.1 (see §5).
22. **Every test that touches an LLM configures the mock via a fixture, not a monkeypatched network call** (`conftest.py:56-65`, used throughout `tests/`) — `dspy.settings.configure(lm=llm)` once per test. `[adopt]` — directly the shape of fixture kohaerenzprotokoll needs for `rlm_ingest.py`'s and the fold-optimizer's offline tests.
23. **Tests assert on the actual rendered LM prompt, not just the parsed output** (`tests/dspy_optimizer/refiner/test_refiner.py:53-65`, `test_evaluator.py:38-47`) — pulls `mock_llm.history[-1]["messages"]` and asserts specific input strings appear in the system/user message. `[adopt]` — good test pattern: catches "I passed the field but the Signature never actually renders it" bugs, which is exactly the shape of silent failure P12/P26 worry about ("a model never types an identifier... code does" — this pattern would catch a signature silently dropping a line-number field before it ever reached a real LLM).
24. **Registry raises on duplicate registration** (`registry.py:17-18`) — `register(name)` raises `ValueError` if `name` is already taken, preventing a second strategy from silently shadowing the first. `[adopt]` — small but correct; matches "a guard reports what it could not check" ethos by making a real class of bug (accidental strategy override) loud instead of silent.
25. **`pyproject.toml` records `ruff`/`black`/`mypy --strict`/90%-coverage targets in `DESIGN.md` even though CI enforcing them is not visibly wired up in this snapshot** (`DESIGN.md:86-102`, no `.github/workflows` found in the file listing) — `[catalogue]` — the standards table itself (line length, docstring style, naming, frozen dataclasses, uv-as-single-source) is a decent checklist to lift wording from for a kohaerenzprotokoll coding-conventions note, but note it is aspirational/undemonstrated here (P2: describe no more than exists — this repo itself does not fully honor that principle, see §4).
26. **`optimize()` returns the final prompt as a plain string**, not a wrapped object (`optimizer.py:195`) — the caller decides what to persist. `[skip]` — trivial, no transferable idea beyond "keep return types simple."
27. **Tests are organized 1:1 with source module paths** (`tests/dspy_optimizer/strategies/merger/test_block_based.py` mirrors `dspy_optimizer/strategies/merger/block_based.py`) — `[catalogue]` — unremarkable but consistent; fine convention to keep if kohaerenzprotokoll's scripts ever grow a `tests/` tree of their own (currently `selftest.py` is a single flat file, which is fine at current size).

## 3. Directly reusable for the target

- **Job 1 (one-term-or-two, DSPy ladder LabeledFewShot→…→GEPA):** `evaluator.py`'s `with_instructions` pattern is the correct way to swap in each rung's compiled instructions without mutating shared state — reuse the *technique*, not the file, since the target's signature (`Surface1, Surface2 -> same_term: bool` or similar) is unrelated to invoice extraction. The `tests/conftest.py::MockLLM` can be copied close-to-verbatim as the offline fixture DSPy tests need (P5); it already proved compatible with DSPy 3.3.1 in this scan.
- **Refiner/self-critique loop (`optimizer.py`, `refiner/refiner.py`, `refiner/signature.py`):** relevant only as *inspiration*, not adoption, for a possible future "propose a `rule` in words for a judgement the code got wrong" step — but note P13 forbids mechanizing conflict detection, and the target's `rule` field is human-written for exactly that reason; the refiner's job here (patch a prompt) is a different kind of task than "explain a human disagreement," so treat this as a pattern reference, not a component to import.
- **Callback system (`callback/base.py`, `callback/history_callback.py`):** the most concretely reusable piece for **the target's planned `--trace` mode and cost visibility** (open problem in the brief). `HistoryCallback`'s `_log_event` shape (`{"event": ..., **state}` appended to a list) is a two-line pattern that could back a `--trace` flag on any future kohaerenzprotokoll DSPy call site; would need (a) JSON-safe serialization of `dspy.Example`/`dspy.Prediction` and (b) an actual cost/token hook added, since none exists here (see §4).
- **Job 3 (RLM census extraction) / Job 4 (skill descriptions via GEPA):** nothing here transfers directly — no RLM usage, no GEPA usage, no skill-description optimization anywhere in this repo (grep confirms zero hits for `RLM`, `GEPA`, `InferRules`, `SIMBA` across `dspy_optimizer/`).
- **Registry pattern (`strategies/registry.py`):** could genuinely back `scripts/rules/` if the target wants string-selectable rule strategies (e.g. `account.py --rule fold_v2`) instead of direct imports; small, dependency-free, ~30 lines, easy to vendor or reimplement.

## 4. Conflicts with the principles

1. **Trivially-true validators on empty input** — `BatchedTrainingSetValidationStrategy.forward` (`strategies/validation/batched.py:54-55`, `if not dataset: return True # An empty dataset trivially passes.`) and `SampleValidationStrategy.forward` (`strategies/validation/sample.py:65-66`, `if not sample_set: return {"is_valid": True, "score": 1.0} # Vacuously true`) both return a **passing** result for zero examples. This is exactly the shape of trap P23/P27 warn against — "a coverage term that returned 1.0 whenever no gold fragments were passed" is the target's own retired-pipeline failure mode, and this repo reproduces the pattern verbatim (silent, undetected "perfect" score on empty input). Any reuse of these strategies must add a P23-style guard: refuse or flag rather than return true.
2. **Documentation outruns what exists** — `README.md` and `DESIGN.md` both describe `examples/dutch_invoices/{optimize.py,dataset.py,data/}` as implemented (`README.md:75-78`, `DESIGN.md:83-87`, checked off in the "Implemented Features" list at `README.md:153`), but no `examples/` directory exists anywhere in the repo (confirmed via `find`). This directly violates the target's own P2 ("describe no more than exists") — the exact defect kohaerenzprotokoll's `state.py --prose` was built to catch.
3. **No cost or token accounting anywhere** — grepped `dspy_optimizer/` for `cost`, `token`, `usage`: the only hit is the test fixture's dummy `_hidden_params={"response_cost": 0.0}` (`tests/conftest.py:52`) and `usage={"prompt_tokens": 0, ...}` in the same mock. Nothing in `optimizer.py`, the callbacks, or the strategies reads real LM usage/cost off `dspy.settings.lm.history` or a similar API. The target's stated need for "cost/trace visibility of LM calls" is **not answered** by this repo — it would have to be added, not borrowed.
4. **`print()`-based logging inside the core loop**, contradicting the repo's own stated standard — `optimizer.py:95-103,108,120-121` uses bare `print(...)` for per-example pass/fail and refinement-attempt logging, while `DESIGN.md:97` mandates "Standard `logging` lib. No `print` except in CLI demos." `[catalogue as a trap]` — a repo's own coding standard doc can drift from its code exactly the way kohaerenzprotokoll's own README warns about; worth remembering as a second, independent example of the same failure class before importing anything wholesale.
5. **`optimizer.py` assumes exactly one output field** (`example_summary = ...list(expected_outputs.values())[0]`, `optimizer.py:118,125,133`) — silently picks `list(expected_outputs.keys())[0]`/`values())[0]` with no check that there is exactly one; a multi-field gold example would silently score/refine against only the first field found by dict ordering. This is not flagged anywhere (no guard, no test for multi-output examples) — a silent, unannounced narrowing of scope, the opposite of "a guard reports what it could NOT check" (P23).
6. **No explicit non-empty/language assertion on any string field** — nothing in `evaluator.py`, `refiner/refiner.py`, or the scorers asserts a non-empty prompt/output or a language constraint; P19 ("assert non-empty + German") has no analogue here since the repo is deliberately domain-agnostic English/Dutch — expected, but worth naming so nobody assumes this repo already does that checking.
7. **`BlockBasedMerger` merges *prompt text*, never *data*, and this is fine** — noted here explicitly because the brief asks to distinguish the two: this repo never merges two labelled examples, two documents, or two sources' factual readings into one; the only thing it ever merges is one canonical, single-owner prompt string with one incoming patch. It therefore does **not** collide with P13 ("never merge two sources' readings"), and is not a trap — but it also means the "merger" name is a false cognate for anything in the target's reconciliation pipeline; don't let the word "merger" import an assumption about merging term readings.

## 5. Dependencies & cost

- **Python:** `pyproject.toml:9` requires `>=3.12` (matches `.venv-dspytools`'s 3.12, not `.venv-dspy`'s 3.11). Would need its own venv (e.g. `.venv-dspy-opt`, 3.12) alongside the target's existing four — no conflict since venvs are isolated, but it cannot live inside `.venv-dspy` without bumping that venv's Python.
- **DSPy version:** declared `>=2.6.27`; `uv.lock` pins exactly `2.6.27` (`uv.lock:745,772`). Verified in this scan: the actual `dspy_optimizer` code (evaluator, refiner, merger, validators, scorers) runs and all 37 non-mlflow tests pass unmodified under **DSPy 3.3.1** too (`env -u UV_EXCLUDE_NEWER uv run --isolated --with dspy==3.3.1 --with pytest --with tqdm python -m pytest tests/ -q --ignore=tests/callback/test_mlflow_callback.py` → `37 passed in 0.84s`). So it can sit beside the target's pinned DSPy 3.3.1 without moving that pin.
- **`mlflow` dependency:** heavy (pulls numpy/pandas/pyarrow/scikit-learn/sqlalchemy/etc., ~200MB+ of wheels). Only needed for `MLflowCallback`; everything else (core loop, `HistoryCallback`, all strategies) needs none of it. In an `--isolated` uv resolution against `dspy==3.3.1` + `mlflow` + numpy for py3.12, the mlflow test hit a `RecursionError`/`TypeError: data type 'bool' not understood` while importing `numpy` — looks like a resolver picking an old numpy incompatible with the interpreter/mlflow combo in isolation, not a `dspy_optimizer` bug (the non-mlflow 37 tests pass cleanly in the same kind of isolated run). If porting `MLflowCallback`'s idea, prefer reimplementing the two hooks it needs (`log_params`/`log_metrics`/`log_text`) against a lighter sink, or just use `HistoryCallback`'s pattern with a JSON file — no MLflow needed.
- **Other deps:** `attachments`, `pytesseract` (OCR — for the *described but absent* Dutch-invoice PDFs; irrelevant to a text corpus), `tqdm` (trivial, fine to keep or drop). None of the core `dspy_optimizer` package's non-test code imports `attachments` or `pytesseract`.
- **API keys:** none required to run any of the 43 tests — confirmed offline, `MockLLM` throughout, `dspy.settings.configure(lm=llm)` per test, zero network calls observed. A live run (not present in the repo) would need whatever LM key `dspy.LM(...)` is pointed at, same as any DSPy program — no project-specific key beyond that.
- **Install footprint if only the reusable parts are lifted:** `dspy_optimizer/strategies/registry.py`, `callback/base.py`, `callback/history_callback.py`, and `tests/conftest.py::MockLLM` together need **zero** extra dependencies beyond DSPy itself already installed in `.venv-dspy`.

## 6. Verdict

The single most valuable thing to take is **`tests/conftest.py`'s `MockLLM`** (lines 9-53) plus the **`HistoryCallback` audit-hook shape** (`callback/base.py` + `callback/history_callback.py`) — together they are a ready-made, DSPy-3.3.1-compatible recipe for an offline test fixture (P5) and a zero-dependency `--trace` log, both of which the target needs and neither of which exists yet. Leave the `PromptOptimizer`/`Refiner`/`Merger` loop itself: it solves "iteratively patch one owned prompt," a different problem from "reconcile many human-owned readings of a term," and its two vacuous-pass validators (empty dataset/sample → `True`) are a live instance of exactly the "coverage=1.0-on-nothing" bug class the target's own `selftest.py` was built to catch — copy the shape only with that guard added. The invoice example referenced throughout the README/DESIGN does not exist in the repo; treat every claim about it as unverified documentation, not evidence of a working end-to-end run.
