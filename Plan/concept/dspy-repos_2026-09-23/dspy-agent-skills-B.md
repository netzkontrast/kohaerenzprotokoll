## 1. What it is

A pack of 32+ Claude Code / Codex "skills" (Markdown instructions + `reference.md` + a `--dry-run` Python smoke test each) teaching agents to build/optimize/ship DSPy programs, targeting **DSPy 3.3.1** (floor `>=3.3.0,<3.4`, `dspy==3.3.0` in the underlying book repo). The nine `dspy-book-*` skills (chs. 1–11 of "Context Engineering with DSPy", an O'Reilly companion repo, MIT) are documentation-as-skill: each distills one book chapter's notebooks, states what the chapter got wrong, and ships a deterministic `--dry-run` example requiring no LM/network/API key. Maturity: well-tested for what it is (`pytest tests/`, 633 passed per CHANGELOG; every book example's dry-run passes on 3.3.1) but the *content* is documentation of someone else's notebooks, not battle-tested library code — several of its own "gaps" and "do not copy" sections say the underlying chapters are unclean (leakage, test-set contamination, non-resolving model IDs). Two docs (`docs/kohaerenz-protokoll-plugin-plan.md`, `docs/compounding-wiki-extension-plan.md`) and `scaffolding/kp_canon_retriever.py` are **written specifically about a "Kohärenz Protokoll" project** — but they describe a structure (`Canon/`, `Manuscript/`, `tools/kpwiki/`, `.agency/session.db`, agency engine, `Plan/drafting/decision-log*.md`, D-01…D-21, `Codex/*.md` with a closed `kind` enum) that **does not match the current target repo's CLAUDE.md** (`Sources/`, `Wiki/`, `Legacy/`, `scripts/state.py`, `Plan/decisions/` one file per decision, no Canon/Manuscript/agency engine/kpwiki anywhere). Treat these two docs as describing an earlier or different incarnation of the target project — useful for transferable ideas, not as an accurate map of today's repo (see §4).

## 2. Every good idea

1. **Metric routing table by output shape** — `dspy-book-metrics/SKILL.md:35-46`. A "your output is X -> use metric Y, watch for Z" table synthesized from the book's ladder (exact match / regex / keyword overlap / edit distance / embedding cosine / token F1 / BLEU-ROUGE / calibrated judge / rubric / trace-aware feedback). `[adopt]` — directly answers "what metric for one-term-or-two / entity-F1", saves re-deriving the shape-to-metric mapping.
2. **Binary-vs-partial-credit gradient argument** — `dspy-book-metrics/SKILL.md:48-62`, `example_metric_recipes.py:38-52` (`gives_gradient` helper: "a metric an optimizer can climb takes more than two distinct values"). `[adopt]` — this is exactly the argument for why `fold()`'s 65% binary baseline needs a continuous companion signal before GEPA can improve one-term-or-two; the `gives_gradient` assert is a one-line unit test worth copying verbatim.
3. **LLM-judge calibration protocol with a stated trust bar** — `dspy-book-metrics/SKILL.md:64-84`, `reference.md:94-123`. Concrete 6-step recipe: label 20-50 by hand with `num_threads=1` (or prompts interleave) and always capture *why*; train a judge Signature (`is_good: bool`, `reasoning: str`) with `BootstrapFewShot` on 80%; measure agreement on held-out 20%; trust only at 80-90%+; promote the judge's own `reasoning` into the GEPA feedback string. `[adopt]` — this is a ready template for calibrating a Jev-based or LM-based one-term-or-two judge against the 26-example trainset, though n=26 is far below the chapter's 20-50-labels-per-class assumption (see §4).
4. **Agreement-without-chance-correction caveat** — `reference.md:121-123`: "There is no chance correction, so 80% on a balanced binary task is closer to 60% corrected — treat 80-90% as a floor, not a ceiling." `[adopt]` — a one-line correction worth attaching to any judge-calibration writeup; directly relevant to scoring one-term-or-two against a small, possibly-imbalanced label set.
5. **Weighted rubric sanity check at both extremes** — `SKILL.md:86-97`, `example_metric_recipes.py:121-139` (`normalize_rubric`, asserting best->1.0, worst->0.0, and rejecting weights that don't sum to 1.0). `[adopt]` — cheap, directly copyable pattern if the target ever scores something on several axes (e.g. a census's quality).
6. **Trace-aware per-predictor feedback, dual-mode metric** — `SKILL.md:102-120`, `reference.md:143-163`, and independently in `dspy-book-eight-steps` (`example_eight_steps.py:79-84`). One function returns a plain score for `dspy.Evaluate` and a `dspy.Prediction(score, feedback)` when `pred_name` is set (an optimizer is asking). `[adopt]` — "widen every metric to five args now, it costs nothing" (SKILL.md:138) is exactly the P26-adjacent discipline the target should bake into any metric it writes for step 1 (one-term-or-two) from day one, even before GEPA is on the table.
7. **Gaps the metrics chapter never states, named explicitly** — judge gaming (re-measure agreement after optimizing, not only before), position/length bias in judges, devset overfitting from repeated optimization against one set, cosine similarity's blindness to negation. `SKILL.md:122-129`. `[adopt]` — P27 (score against human ceiling) pairs directly with "re-measure agreement after optimizing against the judge," which the target has not yet built into its one-term-or-two ladder plan.
8. **"Do not copy" list, sourced from actually reading the notebooks** — e.g. the book's `MultiHopQA` uses a hardcoded public ColBERT endpoint that is "often unreachable" (`reference.md:176-180`); model IDs throughout are book-internal placeholders that don't resolve. `[catalogue]` — general caution: nothing here to adopt directly, but the pattern of naming exactly what NOT to copy (with file:line) is itself a documentation convention worth imitating in the target's own learnings files.
9. **`with_inputs()` as the single point where types/labels get fixed** — `dspy-book-datasets/SKILL.md:24-45`. Coerce types and map labels at conversion time, never inside the metric; a left-out input field silently starves the program, a left-in gold field silently leaks the answer. `[adopt]` — directly transferable rule for turning `Plan/trainsets/surface-pairs.jsonl` rows into `dspy.Example`s for the one-term-or-two ladder.
10. **Difficulty stratification (clear / boundary / ambiguous), and ambiguous cases go to a log, not training** — `SKILL.md:47-61`, `reference.md:44-52`. "They tell you where the task definition itself is incomplete" — an ambiguous case is a specification finding, not a model failure. `[adopt]` — maps almost exactly onto the target's `Negentropie`/`Entropie`=NEVER-merge distinction and any future ambiguous surface pair: route it to a decision file / OpenQuestion, not into the 26-example trainset as noise.
11. **Error notes as the feedback channel — dataset ships the diagnosis, not just the label** — `SKILL.md:63-72`, `reference.md:55-72`. A `notes` field written during error analysis ("model sees X and assumes Y, but it's Z") is passed straight through as the GEPA feedback string. `[adopt]` — the target's `Plan/trainsets/surface-pairs.jsonl` already has a human-written `rule` in words per example (per BRIEF.md); this is confirmation that the `rule` field is exactly the right shape to feed a GEPA-compatible metric's feedback, and a reason to never drop it when converting to `dspy.Example`.
12. **Seeded, disjoint splits with an executable disjointness check** — `SKILL.md:73-84`, `reference.md:22-42`, `example_dataset_builder.py:63-70` (`splits_are_disjoint`). `random.Random(2024).shuffle(...)`, never bare `random.seed()`. `[adopt]` — small, free, and the dataset skill explicitly documents that the book's own chapters violate this (chapter 3 evaluates on training rows; a notebook optimizes against a slice of its own test set) — good cautionary evidence to cite when writing the target's own no-leakage checklist.
13. **Small-corpus split sizes vs large-corpus split sizes, stated as two different regimes** — `reference.md:33-42`: hand-built set gets 50/25/25; a "large public corpus" gets 200 train / 100 val / 500 test with disjoint index ranges. `[adapt]` — the target's n=26 is far below even the "hand-built" 50/25/25 assumption (would be ~13/6/7); worth noting explicitly that the book gives no guidance at all for n<30, which is a real gap (see §4/§3).
14. **Enrichment > generation for synthetic data** — `SKILL.md:109-113`, `reference.md:99-111`. When you have real outputs but not the inputs your signature needs, write the inverse signature and infer inputs; "a real joke with a synthesized topic is far better training data than a synthesized joke." `[catalogue]` — plausible technique if the target ever wants to expand beyond 26 hand-labelled pairs (e.g. take a real wiki merge/split decision and synthesize the *reason text* around it) — but P4 ("no field/type/check without real instances") argues against inventing surface pairs synthetically at all; catalogue only, do not build yet.
15. **`n=15` completion-count assertion and dedup-before-trusting synthetic batches** — `SKILL.md:104-107`, `example_dataset_builder.py:92-99` (`synthetic_batch_is_sound`). Some endpoints silently return fewer completions than requested and `zip()` truncates without error. `[catalogue]` — only relevant once/if the target ever calls a model with `n>1`; not close to being used yet, but cheap to remember.
16. **PII synthesis caveats, generalizable to "quoting research documents"** — `SKILL.md:114-122`. Three unstated risks: the real text still reaches the provider even when synthesizing "fake" data from it; nothing verifies the synthetic output actually dropped identifiers; nothing checks the model didn't echo a real name. `[catalogue]` — analogous risk if the target ever sends corpus text to Jev/TypeSafe or an LM for any judge/extraction task: the same three checks (diff/regex before trusting) apply, worth carrying into `Plan/concept/jev-in-ingestion` review.
17. **Measured optimizer ladder, real numbers, real regressions** — `dspy-book-optimizers` entire skill (`SKILL.md:30-73`, `reference.md:31-56`). Twelve optimizers on one fixed task: two (COPRO, SIMBA) score *below* the unoptimized baseline; the two free optimizers (`LabeledFewShot`, `KNNFewShot`) beat six paid ones; MIPROv2 shows a 10.4-point validation-to-test overfit gap while GEPA is the only run where val==test exactly; cost does not rank quality (SIMBA is the most expensive AND the worst). `[adopt]` — this is the strongest evidence-backed argument for the target's own planned ladder order (LabeledFewShot -> BootstrapFewShot -> InferRules -> SIMBA -> GEPA): it validates "start free, escalate only on a measured plateau," and it is a documented, citable warning that SIMBA specifically can regress and cost the most at once — worth flagging before the target spends budget on SIMBA at n=26.
18. **"Optimizing can make it worse" — a baseline-and-held-out-test discipline is what lets you detect a regression at all** — `SKILL.md:53-58`. `[adopt]` — directly reinforces target's P24 ("done is a measurement") and P27 (score against human ceiling): build the disjoint baseline test before running any optimizer on the one-term-or-two task.
19. **`dspy.Ensemble` is not a trainable optimizer — no trainset, no metric, only a program list, and its accuracy gain is a permanent per-inference cost multiplier (3.7x eval cost, 2.7x latency)** — `SKILL.md:115-121`, `reference.md:78-93`. `[skip]` for the target now — n=26 is too small to build multiple candidate programs to ensemble, and the target has no serving-latency budget concept yet; `[catalogue]` for later if a served one-term-or-two classifier ever needs an accuracy bump.

59. **MMR (Maximal Marginal Relevance) selection with a relevance floor, and a measured proof that the floor changes the outcome at every diversity setting** — `scaffolding/kp_canon_retriever.py:92-143` (`select_mmr`), documented also in `docs/kohaerenz-protokoll-plugin-plan.md:106-114` and `docs/CHANGELOG.md:155-157`. Plain MMR scores an irrelevant passage `0-0=0` and a relevant near-duplicate slightly *below* zero, so at any diversity weight from 0.5 to 0.8 without a floor, MMR picks the irrelevant passage over the near-duplicate-but-relevant one; adding a `min_relevance` floor fixes this at every setting tested, while raising the diversity weight alone never does. `[adapt]` — this is a real, measured bug-and-fix, not speculative. It is directly relevant to the target's qmd search question ("which qmd search backend is best (never benchmarked)") if the target ever builds its own passage-selection layer on top of qmd hits rather than relying on qmd's own reranker; also directly relevant to job 3 (RLM ingest) if candidate-line retrieval for a census ever needs deduplicated top-k selection over a dense, repetitive corpus (the target's corpus is described as "dense with related entries" in spirit, per the codex analogy). The code itself (`select_mmr`, `cosine`, `CanonIndex._shortlist`/`_select`) is small, dependency-free, and vendorable.
60. **A `CanonRetriever`-shaped callable seam, injected with a no-op default (`no_canon_retrieval`), reversible by argument, testable offline via a deterministic lexical fallback when no embedder is passed** — `scaffolding/kp_canon_retriever.py:161-209`. `[adapt]` — the injected-callable-with-a-safe-default pattern (compare `no_canon_retrieval` to `fold()`'s deterministic baseline, or to `Wiki/index.json` lookup in `reconcile.py`) is exactly the shape the target already uses for `reconcile.py`'s O(census)+O(judgement) lookup; nothing to port literally (the class targets a different repo's `Claim`/`SourceIngest` types), but the pattern of "ship the seam with a deterministic offline fallback, let an embedder be optional" is directly reusable if the target ever wants a semantic-search layer behind `Wiki/index.json` lookup.

## 4. Conflicts with the principles

- **P4/P3 "by hand first; no field/type/check without real instances."** The two KP-specific plan docs and the scaffold describe and half-build features (`CanonRetriever`, a `Learning` typed model, a suppression mechanism, a `kind` enum migration) for a repo structure that does not exist in the current target (`Canon/`, `Manuscript/`, `tools/kpwiki/`, `.agency/`, D-01…D-21 decision log with a fixed table shape, a "codex" with a closed kind enum) — none of this matches `kohaerenzprotokoll`'s actual `Sources/`/`Wiki/`/`Plan/decisions/` layout. If ported literally, this would be exactly the failure P4 warns against: building fields/checks against a structure that was never verified against the real repo. Treat both plan docs and the scaffold as ideas-with-evidence-elsewhere, not as ready specs — every file path and type name in them needs re-deriving against the actual target repo before any code is written.
- **P26 "a model never types an identifier or line number — code does."** The book's own eleventh-chapter recipe is compatible with this (the model writes the SKILL.md text; nothing in `optimize_anything`'s contract has the model emit a citation or line number). No direct conflict found in the book skills. The compounding-wiki-extension-plan's `Learning.citation` field (reusing a `Citation` model) is explicitly designed to *require* a verifiable line per the plan's own P3-equivalent — consistent with, not against, the target's rule — but again, it's a plan for a repo the target isn't.
- **P18 "repeats, cache off."** Nothing in the material I scanned (dspy-book-production included) states how to turn the DSPy cache off; the book-production skill explicitly hands cache hardening to the separate `dspy-production` skill (outside PART B's scope). This is a real gap in what I read: if the target relies solely on the book skills for a "how do I disable cache for reliability measurement" recipe, it will not find one here.
- **A metric that cannot fail.** `dspy-book-metrics` and `dspy-book-eight-steps` both explicitly warn against exactly this shape (binary metrics with no gradient, an uncalibrated judge, `judge_metric`'s plain agreement with no chance correction) — these are *consistent* with the target's P24/P27, not a conflict, but worth citing back to the target's own "coverage term that returned 1.0 whenever no gold fragments were passed" postmortem as external confirmation the failure mode is common and named in the wild.
- **Silent data loss as a design trap.** `optimize_anything`'s introspected-parameter-name requirement (item 23) is a real, sharp instance of a tool violating the spirit of P23 ("a guard reports what it could NOT check") — the tool itself gives no error at the call site, only a deep crash later. This is not the target's own code, but if the target ever calls `gepa.optimize_anything` directly (job 4), it must add its own guard (`evaluator_signature_ok`) rather than trust the library to fail loudly — worth building that guard *before* the first real call, not discovering it the hard way.
- **No InferRules coverage anywhere.** The brief names `InferRules` as a step in the target's planned optimizer ladder; a repo-wide grep found zero mentions of `InferRules` in this entire pack (skills, articles, docs, scaffolding). This scan cannot confirm or deny any of PRINCIPLES-relevant guidance for that optimizer from this source.

## 5. Dependencies & cost

- Book skills (`dspy-book-*`) require only `dspy` (pinned `>=3.3.0,<3.4` for this pack; the underlying book repo pins `dspy==3.3.0`) and, for the coding-agents skill specifically, the separate **`gepa` package** (`gepa==0.1.1` per `reference.md:3`) since `optimize_anything` lives there, not in `dspy`. ## 6. Verdict

The single most valuable thing to take is the **`dspy-book-coding-agents` recipe for `gepa.optimize_anything`** (items 22-29): it is a complete, small-dataset-compatible (5-20 real failures), directly-cited, trap-annotated playbook for exactly the target's job 4 (GEPA-optimizing `.agents/skills/*/SKILL.md` descriptions), and it needs only the `gepa` package added beside the existing DSPy 3.3.1 pin. Close behind is the **measured optimizer ladder** (`dspy-book-optimizers`, item 17), which is real evidence — not speculation — that the target's planned free-first-then-escalate order is sound, and a specific, citable warning that SIMBA can regress and cost the most at once.

Leave the two Kohärenz-Protokoll-specific plan documents and the `kp_canon_retriever.py` scaffold as **catalogue only, not ready code**: they were written against a repo structure (`Canon/`, `tools/kpwiki/`, an agency engine, a D-01…D-21 decision log) that this scan's own read of the target's current `CLAUDE.md` shows does not exist today. The MMR-with-relevance-floor code inside that scaffold is a genuine, dependency-free, measured idea worth lifting on its own merits — but the surrounding plan's file paths, class names and "Part 4 sequence" should not be trusted as a map of the real repo without re-verifying every path against `kohaerenzprotokoll` directly first.
