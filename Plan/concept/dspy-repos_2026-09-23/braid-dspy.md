# Scan: braid-dspy (`/home/user/braid-dspy`)

## 1. What it is

A small (0.2.3, "Alpha") pure-Python package wrapping the BRAID two-phase
reasoning idea (plan a Mermaid flowchart "GRD", then execute it node by node)
as a DSPy module. Author calls it "vibe coded" (README.md:21) after watching a
livestream and reading a vendor blog post — it is not a reproduction of a peer
reviewed paper, just one blog's architecture description implemented from
scratch. Targets `dspy-ai>=2.0.0` (pyproject.toml:29, requirements.txt:1),
i.e. the pre-3.x DSPy API (`dspy.OpenAI`, `dspy.Predict`) — not verified
against DSPy 3.3.1. 185 unit/integration tests pass offline in ~10s with no
API key (`pytest tests/ -q`, verified in this scan). CI runs the same suite on
3.9–3.11 with 70% coverage gate plus `black --check` (`.github/workflows/ci.yml:32,60`).
No evidence of a real (non-synthetic) benchmark run anywhere in the repo —
GSM8K "example" is 5 hardcoded problems, never actually executed against a
model and no result committed (`examples/gsm8k_example.py:13-26`).

## 2. Every good idea

1. **Plan-then-execute as two DSPy signatures** — `BraidPlanSignature` (problem → GRD) and `BraidStepSignature` (step_description, context → step_output), wired by a `dspy.Module.forward` that parses the GRD and loops over nodes. `braid/module.py:26-237`, `braid/signatures.py:6-89`. `[adapt]` — the actual pattern (freeze a plan, then let determinate code drive execution) is exactly what the target's `reconcile.py`/`account.py` already do by lookup rather than by model; useful as a second example of the shape, not as code to import.
2. **Mermaid as the plan's storage/interchange format** — a GRD is literally the DSPy output string, parseable, diffable, and human-viewable in any Mermaid renderer. `braid/parser.py:1-332`. `[catalogue]` — Mermaid could be the render layer for `Wiki/index.json`'s relation graph (`relations.py`) or for a one-term-or-two decision tree, since it is copy-pasteable into a page and every git diff of the flowchart source is a diff of the plan.
3. **Topological execution order derived from the graph, not asserted by the model** — `GRDStructure.get_execution_order()` does Kahn's algorithm over the *parsed* edges; the model never states step order directly. `braid/parser.py:71-97`. `[adopt]` — directly matches P1/P12: the model proposes structure, code computes order/identifiers. A one-term-or-two "compare referents → check prefix → decide" procedure could be encoded as GRD nodes and the traversal order computed the same way, with code (not the model) walking it.
4. **Structural validator that is separate from and prerequisite to semantic scoring** — `MermaidParser.validate()` raises/returns false before anything else runs; `StatefulExecutionEngine`/`BraidReasoning.forward` refuse to execute an invalid plan. `braid/parser.py:288-302`, `braid/module.py:121-136`. `[adopt]` — a "guard reports what it could NOT check" pattern (P23): a plan a program can't parse never gets silently executed.
5. **A validator that returns *both* a boolean and a numeric score with itemized issues** — `ValidationResult(valid, issues, score)`, each `ValidationIssue` carries severity/code/message/node_id/suggestion. `braid/validators.py:25-66`. `[adapt]` — the "issue objects with a machine code plus a human message" shape is reusable for `quotes.py`/`selftest.py` style checkers that currently print ad hoc strings; a structured issue list is easier to assert on in tests and to render consistently.
6. **Node atomicity as a measurable proxy metric ("≤15 tokens/node")** — `AtomicityValidator.count_tokens` + a cited empirical claim from the BRAID paper that nano-models do better with short atomic steps. `braid/validators.py:69-203`. `[skip]` — the "≤15 tokens" number is asserted, not measured in *this* repo (no dataset, no accuracy delta shown); adopting the metric without the backing measurement violates the target's "a claim is measured, or marked unmeasured" rule. The *idea* of "score node granularity as a proxy for parseability by a small model" is worth keeping in the catalogue, though.
7. **Numerical masking to stop the planner leaking the answer into the plan** — `NumericalMasker.mask/unmask/detect_leakage`, regex-based, with an explicit `EXCLUDE_PATTERNS` list for false positives like step numbers. `braid/masking.py:38-349`. `[catalogue]` — analogous problem to "a census must not use accumulated wiki state to decide what's in a document" (extraction's independence, CLAUDE.md "Extraction's independence…"); the masking *pattern* (detect classes of leak, whitelist known non-leaks, report count) is a generic technique worth remembering even though the domain (currency/units) doesn't map to German prose terms.
8. **`detect_leakage` as an audit-only, non-blocking check** — separate from `mask()`; it just enumerates suspicious patterns with position + context for a human/log to review. `braid/masking.py:258-293`. `[adapt]` — same shape as `quotes.py`'s "checked vs uncheckable" reporting: a checker that flags candidates without asserting truth.
9. **Regex "exclusion window" technique** — before masking a number, it re-scans a ±10-char context window against an exclude-pattern list and only rejects if the excluded match's span actually overlaps the candidate span (not just co-occurs nearby). `braid/masking.py:130-145`. `[adapt]` — a genuinely reusable string-matching trick for any "don't flag this token if it's part of a larger, allowed pattern" checker (e.g. avoiding false line-citation flags near headings/citation markers, which `quotes.py`'s "73 unmarked mentions… inside a quotation, citation line, or heading" problem resembles).
10. **Conditional branching parsed from Mermaid edge labels** (`-->|label|`), evaluated at runtime by a small `ConditionEvaluator` supporting boolean keywords, numeric comparisons, and `contains`. `braid/engine.py:100-196`. `[catalogue]` — a lightweight condition-DSL-in-labels idea; could inform how a reconciliation flowchart branches on "found in wiki index? yes/no" without inventing a new DSL.
11. **Explicit iteration caps per node and total-step caps to stop infinite loops in a cyclic plan** — `max_iterations_per_node`, `max_total_steps`, `ExecutionState.get_iteration_count`. `braid/engine.py:209-298`. `[adopt]` — any executable plan representation for the target (e.g. a judgement retry loop) needs the same two caps; simple and correctly placed before execution rather than after.
12. **Cycle detection as its own read-only method, independent of execution** — `has_cycles()` (DFS) and `detect_cycles()` (enumerate all cycles) on the parsed graph, callable before ever running anything. `braid/engine.py:456-505`. `[adopt]` — cheap, decidable, and a good "check what you can before you spend a model call" pattern (P1).
13. **Critic nodes detected by label prefix, not by a special node type** — `CriticDetector` matches `^Check:`, `^Verify:`, `^Confirm:` etc. on the plain node label, then locates the "fallback" (retry) edge by scanning outgoing edge labels for failure keywords. `braid/critic.py:56-163`. `[skip]` — brittle (English-only, prefix-anchored regex) and *does* mechanize a judgement (does verification pass?) via keyword counting — see conflicts section. Worth knowing the failure mode, not the code.
14. **A confidence score derived from how *unambiguous* the pass/fail signal was, not from calibration** — `CriticEvaluator.evaluate` computes `max(success_count, failure_count) / total_indicators`, defaulting to 0.5 when there's no signal. `braid/critic.py:262-268`. `[skip]` — looks like real uncertainty but is just a lexical count ratio; exactly the "coverage metric that can't fall" trap the target explicitly warns about (P24, the `coverage()`-returns-1.0 anecdote). Good negative example to cite.
15. **Two-model cost model (architect vs solver) with per-phase token tracking** — `PPDAnalyzer.track_usage(usage, phase="planning"|"execution")`, summed into `CostAnalysis`. `braid/metrics.py:74-247`. `[adapt]` — the *bookkeeping shape* (log every LM call with phase + tokens + latency, derive totals) is exactly what "cost/trace visibility of LM calls" (an open target problem) needs; the target should plug in *real* token counts from `dspy.settings.lm.history`/usage instead of hand-passed `TokenUsage` objects.
16. **A large embedded per-model price table (OpenAI/Anthropic/Google/local), with a documented "as of" date and a graceful unknown-model fallback (`ModelConfig(model_id, 1.0, 2.0, "unknown")`)** — `braid/metrics.py:92-167`. `[catalogue]` — the fallback-on-unknown-model idea is nice; the table itself is stale the instant it's copied (prices already look dated e.g. "gemini-3.0" is speculative/future-dated relative to this repo's Dec-2025 claim) and is exactly the kind of "claim that will silently rot" the target's `state.py --prose` mechanism is built to catch — don't hardcode it, generate it or cite a live source.
17. **PPD score = accuracy / cost, explicitly scaled "per $0.01" for readability, with an explicit `inf` case when cost is 0** — `PPDAnalyzer.calculate_ppd_score`. `braid/metrics.py:275-302`. `[skip]` — the formula itself is fine but every accuracy figure fed into it in this repo is a *hardcoded example number* (`accuracy=0.95` in docstrings and tests), never a measured evaluation result. Nothing in braid-dspy's own repo produces an accuracy from real data — the "cheaper model executes cheaper-model's plan" cost claim is **entirely aspirational**: not measured here at all (see section 4/5).
18. **`compare_with_baseline` estimates the counterfactual single-model cost from BRAID's own tracked token averages** (`avg_tokens * 0.7` as input, `*0.3` as output) rather than a real single-model run. `braid/metrics.py:304-356`. `[skip]` — the 0.7/0.3 split is invented, not measured against a real ungated baseline call; the "efficiency multiplier" the README's Quick-Start example prints is therefore synthetic by construction, not evidence of BRAID being cheaper.
19. **LatencyTracker context manager** — trivial `time.perf_counter()` wrapper. `braid/metrics.py:463-481`. `[adopt]` — small, correct, and exactly what a "keep the timings" artifact policy (target's "Every step keeps its artifact" / `Plan/runs/.../timings`) needs; simplest possible reusable primitive in the repo.
20. **Synthetic-data-generator with parametrized templates + an explicit answer function per template, and a post-hoc validator pass that separates valid/invalid generated samples rather than trusting generation** — `SyntheticDataGenerator.generate_math_samples` + `validate_samples`. `braid/training.py:53-333`. `[catalogue]` — the "generate then validate, keep only what a mechanical checker approves" loop is the right shape (mirrors P5 "offline fixture"), but the *content* (word-problem templates) doesn't transfer to a German term-wiki domain.
21. **Fine-tuning dataset exporter targeting the OpenAI chat format explicitly, factored as a static method independent of the generator** — `ArchitectTrainer.prepare_openai_finetune_dataset`. `braid/training.py:448-483`. `[skip]` — ties training data to one vendor's schema; the target has no fine-tuning plan and DSPy's own optimizers (BootstrapFewShot/GEPA) don't need this format.
22. **Dataset statistics as its own object (`DatasetStats`) separate from generation, computed by re-parsing every sample rather than trusting generation metadata** — `ArchitectTrainer.calculate_dataset_stats`. `braid/training.py:485-540`. `[adapt]` — "trust nothing generation claims about itself; recompute stats by parsing the artifact" is a good discipline, matches `state.py`'s "state is derived, never stored" principle almost exactly. Worth citing as independent confirmation of that principle from an unrelated codebase.
23. **`GRDMetrics.overall_quality` as an explicit weighted sum of six named component scores, with a documented weight vector** — `braid/optimizer.py:206-252`. `[adapt]` — the pattern (name every component, weight them, expose `detailed_quality_report` for the breakdown) is a reasonable template for a future composite "wiki page health" metric, but the specific weights (0.4/0.4/0.2, then 0.15/0.10/0.10/0.25/0.20/0.20) are unjustified magic numbers, not measured — cite the pattern, not the numbers.
24. **`BraidOptimizer` composes with any DSPy teleprompter by handing it a plain `dspy.Example` trainset built from run traces**, i.e. it doesn't reimplement optimization, it just reshapes data for `base_optimizer.compile(...)`. `braid/optimizer.py:315-464`. `[adopt]` — a clean example of "wrap DSPy's optimizer API rather than reinvent it," relevant if/when the target wires GEPA/BootstrapFewShot around `fold()`/one-term-or-two (job 1) or skill descriptions (job 4).
25. **Two-tier prompt construction: hardcoded protocol rules text + a swappable few-shot example list (`DEFAULT_EXAMPLES`, `add_example`)** — `braid/generator.py:16-261`. `[adapt]` — decouples "the rules" from "the demonstrations," which is close to how a target signature/prompt for one-term-or-two would separate the German linguistic rule text from the 26 labelled pair examples.
26. **`extract_mermaid_code` tolerates code fences, language tags, or bare graph/flowchart text, and returns `None` (not an exception) when nothing is found** — `braid/utils.py:7-27`. `[adopt]` — small, well-scoped utility; "explicit non-crashing failure signal for a text-extraction helper" is exactly the right shape for any "pull a structured thing out of free LM text" helper the target might write for a GRD-like plan or for extracting quoted fragments.
27. **CI matrix across three Python minors plus a separate lint job, coverage-gated at 70%, uploaded to Codecov but not blocking on upload failure (`fail_ci_if_error: false`)** — `.github/workflows/ci.yml:9-61`. `[adopt]` — sensible, low-cost CI shape; the "don't fail the whole pipeline because the coverage *upload* failed, only fail on actual test/coverage regression" distinction is worth copying verbatim.
28. **Tests use no mocks for the pure-logic modules (parser/validators/masking/metrics) and only construct dataclasses/module objects directly** — confirmed by reading `tests/test_metrics.py`, `tests/test_optimizer.py`; verified by running the suite (185 passed, no network, ~10s including install). `[adopt]` — matches P5 exactly: an entirely offline, no-key test fixture is the default here, not a special case.
29. **`BraidResult`/`ExecutionResult` always carry an `execution_trace`/`get_execution_trace()` even on partial or failed runs**, so a failed plan still returns a legible list of what happened at each step instead of just an exception. `braid/module.py:12-24,205-224`, `braid/engine.py:76-97`. `[adopt]` — directly serves "every step keeps its artifact"; a trace object is produced whether or not execution finished, which is the right default for a target pipeline step too.
30. **Errors during a single step do not abort the whole run — they're recorded per node and execution continues** — `braid/module.py:214-224`, `braid/critic.py:459-461`. `[catalogue]` — reasonable for a demo/toy pipeline; for the target this trades off against "P23 a guard reports what it could NOT check" — continuing past a failed step silently could hide a defect unless the trace is always inspected. Note the tension, don't copy uncritically.

## 3. Directly reusable for the target

None of this is directly importable as a dependency (see §5 for why), but as *design references*:

- **Job 1 (one-term-or-two)**: `braid/parser.py`'s topological-sort-over-a-parsed-graph pattern (idea #3) and the two-tier rules+examples prompt split (idea #25) are the closest matches. A GRD-style flowchart ("compare referents → check prefix → decide") could literally be written as a small Mermaid snippet and parsed with the same regex approach — but the target should write its own ~50-line parser scoped to its own tiny grammar rather than pull in `braid.parser` (which targets arbitrary Mermaid, has known regex fragility — see §4 — and is coupled to the rest of the package via `braid/__init__.py`'s eager imports of `dspy`).
- **Job 2 (entity lists)**: nothing directly transferable; BRAID has no notion of "entity" or "line citation."
- **Job 3 (census via `dspy.RLM`)**: idea #26 (`extract_mermaid_code`'s tolerant-fence-parsing-with-None-on-failure) is a good template for whatever extracts a structured census list out of RLM output — same shape of problem (pull structure from free text, fail loud/quiet rather than crash).
- **Job 4 (skill description optimization via GEPA)**: idea #24 (`BraidOptimizer` as a thin wrapper reshaping traces into `dspy.Example`s for `base_optimizer.compile`) is a usable pattern reference for wiring GEPA around `SKILL.md` descriptions, though the target would write its own thin wrapper (a handful of lines) rather than depend on `braid.optimizer`.
- **Cost/trace visibility (open problem)**: idea #15/#19 (phase-tagged `TokenUsage` log + `LatencyTracker`) is the most directly liftable *pattern* — a target module could log every real DSPy LM call's `(phase, prompt_tokens, completion_tokens, latency_ms)` the same way, but must source real numbers from `dspy.settings.lm.history` (or whatever DSPy 3.3.1 exposes) rather than the hand-typed `TokenUsage(500, 200)` calls seen throughout this repo's tests and docs.
- Nothing here supplies a "reconciliation procedure" representation beyond the generic graph/flowchart idea already covered.

## 4. Conflicts with the principles

- **Model output enters an executable structure without independent verification that it means what it says** — `BraidReasoning.forward` parses and *runs* whatever Mermaid the LM produced (after only structural, not semantic, validation). `braid/module.py:93-166`. Conflicts with "a model output may direct attention; it never enters the canonical record unverified" — here it doesn't just direct attention, it *is executed*.
- **A metric that cannot fail informatively / "coverage-that-can't-fall" pattern reappears**: `ProceduralScaffoldingValidator`'s "no issues → WEAK_SCAFFOLDING info-only" fallback (`braid/validators.py:290-303`) and `CriticEvaluator`'s confidence-from-count-ratio (idea #14) both produce a plausible-looking score from keyword counting with no ground truth to fail against — precisely the shape of the target's own retired `coverage()` anecdote (P24).
- **Conflict/judgement detection is mechanized by regex keyword matching**: `CriticDetector`/`CriticEvaluator` decide "did verification pass?" via `SUCCESS_PATTERNS`/`FAILURE_PATTERNS` word lists (`braid/critic.py:215-291`). The target's rule is explicit: "Conflict detection is never mechanised. Two readings can only be compared by reading them." This is a direct, named trap: an LLM output containing the word "correct" is automatically treated as a passed judgement.
- **No offline-safe default anywhere in the *runnable, non-test* code path**: `GRDGenerator`/`BraidReasoning` require a configured `dspy.settings.lm` and will raise/loop through retries without one; there is no `--dry-run` fixture pattern for the actual library entry points (only for the test suite, which mocks nothing and never calls a model at all — it tests the deterministic pieces exclusively). This partially satisfies P5 (the *tests* are the offline fixture) but the *examples* (`examples/basic_usage.py`, `gsm8k_example.py`) are not runnable without a live API key and are not marked as such.
- **Silent/implicit caching is absent, but so is any cache-off discipline (P18)** — no caching layer exists in this repo at all, so there's nothing to conflict with directly, but also nothing to learn from for "repeats, cache off."
- **A model may type a numeric placeholder id it invents** (`{{VALUE_1}}`) that downstream code then has to trust matches up 1:1 with what it detected — `braid/masking.py:125-129,199-201`; the *masker* generates the ids (not the model), so this is actually fine and matches the target's "a model never types an identifier or line number — code does" (P12/P26). Included here as a **non-conflict worth noting explicitly**, since it looked at first glance like it might be one.
- **Hardcoded, dated pricing/capability tables presented as current** (idea #16) is exactly the "claim that survived because nobody counted" failure mode the target's `state.py --prose` exists to catch — several entries (e.g. "gemini-3.0-pro/flash") reference model names that postdate this package's stated Dec-2025 update comment, i.e. the table already contains at least one entry that cannot have been empirically priced by the person who wrote it.
- **`pip install braid-dspy`** is the documented install path everywhere (README, docs, integration guide) — conflicts with target's "every dependency goes into a virtualenv, never system Python" only in spirit (it's a normal PyPI package), but is a reminder that if ever adopted it must go through `.venv-dspy` per the target's venv discipline, and its `dspy-ai>=2.0.0` pin should be checked against the target's DSPy 3.3.1 (untested — see §5).

## 5. Dependencies & cost

- **Single runtime dependency**: `dspy-ai>=2.0.0` (`pyproject.toml:28-30`, `requirements.txt:1`). No pin ceiling — could resolve to any DSPy from 2.0 up. **Not verified against DSPy 3.3.1** in this scan (no `.venv-dspy` was touched, per instructions); the code uses `dspy.Module`, `dspy.Predict`, `dspy.Signature`, `dspy.InputField/OutputField`, `dspy.Example`, `dspy.settings.lm` — all APIs that exist in modern DSPy, but README/docs still show `dspy.OpenAI(model="gpt-4")` (README.md:56, docs/index.md:14, docs/integration.md:23), which is the **old, pre-3.x LM constructor style**; DSPy 3.x uses `dspy.LM(...)`. This is a live compatibility risk if the target ever imported `braid` directly against `.venv-dspy`'s pinned 3.3.1 — the library code itself doesn't hardcode `dspy.OpenAI` (only the docs do), so it may still import fine, but the documented usage pattern would not work as written.
- **Dev-only deps** (`pyproject.toml:33-45`): pytest, pytest-cov, black, pre-commit, isort — trivial, no conflict with a throwaway venv.
- **No API keys required to install, import, or run the test suite.** Verified live: `uv run --with-editable . --with pytest --with dspy-ai python -m pytest tests/ -q` → 185 passed in 9.60s, fully offline, no network calls made beyond package resolution. (uv.lock was incidentally touched by this run and has been reverted; the repo was left unmodified.)
- **Footprint**: pulls DSPy's own dependency tree (numpy, litellm, tokenizers, aiohttp, sqlalchemy, grpcio, pillow — ~78 packages, tens of MB) purely to satisfy the `import dspy` in `braid/__init__.py:16` even for code paths (parser, masking, validators, metrics) that don't touch an LM at all. It would sit **beside** `.venv-dspy` without conflicting on the DSPy pin only if the target relaxed `dspy-ai>=2.0.0` compatibility testing to actually confirm 3.3.1 works — untested here.
- Could not live in `.venv-tools`/`.venv-dspytools`/`.venv-typesafe` (wrong purpose); would need its own `.venv-braid` or, better, just be read for ideas and not installed at all, since none of its runtime code is proposed for adoption (§3).

## 6. Verdict

The single most valuable thing to take is the **bookkeeping pattern for LM-call cost/latency tracing** (phase-tagged token log → derived cost/time breakdown, ideas #15/#19) — it is generic, small, and maps directly onto the target's open "cost/trace visibility of LM calls" problem, provided real token counts replace this repo's hand-typed `TokenUsage(500, 200)` stand-ins. Leave the whole package uninstalled: its cost claims are unmeasured aspiration (a hardcoded, already-stale price table times synthetic accuracy numbers, never run against a real baseline), its "critic" verification mechanizes exactly the judgement the target's principles forbid mechanizing, and its DSPy 2.x-era usage examples are unverified against 3.3.1. Read it for the plan/execute-as-parsed-graph shape (Mermaid-as-storable-plan, topological execution order, structural-validate-before-run), not for any function to call.
