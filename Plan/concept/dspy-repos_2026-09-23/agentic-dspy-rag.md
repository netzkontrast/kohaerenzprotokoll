# Scan: Agentic-Dspy-Rag

Full repo read (11 files, ~600 lines total). No modifications made to either repo.

## 1. What it is

A single-author toy/demo repo (`README.md:1`): a multi-agent RAG system in DSPy (`dspy-ai`, pre-2.x style API — `dspy.Retrieve` subclassing, no `dspy.Signature` classes, uses `n=1` on `dspy.Predict`), with intent classification, query expansion, Qdrant vector search, Gemini re-ranking, and a FastAPI endpoint. 7 commits (`git log`: `fa01885` "first commit" through `474f107` "m"). **No tests directory exists anywhere.** No `requirements.txt` (the README tells the user to create one themselves). `src/agentic_rag/_init_.py` files are misnamed — single underscores, not `__init__.py` — so **the package as checked in does not actually initialize as a Python package**; `find_packages()` in `setup.py` would not discover it as-is. Never run here (would need Docker, four API keys, a live PDF). Verdict: unverified-in-practice, all-online, no offline path, no fixtures, no golden set — the opposite of the target's testing culture.

## 2. Every good idea

1. **Intent-classify-then-route orchestrator** — `OrchestratorAgent.forward` (`src/agentic_rag/components/agents.py:107-127`) classifies a question into Factual/Comparative/Multi-step with `dspy.Predict("question -> intent")` and dispatches to a different agent per branch. Simple, legible pattern for an "ask" layer that must behave differently for "what is X" vs "how do X and Y differ" vs a multi-hop question. `[adapt]` — the *shape* (classify, then route to a differently-prompted responder) is reusable for `ask`, but the classifier itself is an un-validated free-text LLM call with brittle string matching (`"Comparative" in user_intent`, `agents.py:115`), which is exactly the kind of unverified judgement P1 asks to name explicitly rather than bury in string containment.
2. **Query decomposition into sub-questions, answered independently, then synthesized** — `MultiStepRAG` (`agents.py:62-90`): `dspy.ChainOfThought("complex_question -> sub_questions")` splits on `;`, each sub-question is answered by a nested `SimpleRAG` instance, and a second `ChainOfThought("original_question, qa_pairs -> final_answer")` synthesizes. This is the multi-hop mechanism the target has none of yet. `[catalogue]` — worth keeping as a decomposition strategy for a future multi-hop `ask` job (e.g. "how does AEGIS's entropy reading in doc A compare to doc B's"), but as written it re-synthesizes into prose without carrying forward the sub-answers' citations, so it would violate P12/P26 unless rebuilt to carry `^[Lnn]` provenance through the merge.
3. **Query expansion for recall** — `QdrantRetrieverWithExpansion.forward` (`data_modules.py:42-69`): before searching, an LLM rephrases the query into 3 variants + original, searches all, dedupes with `dict.fromkeys`. `[adapt]` — the idea (paraphrase a German query several ways before BM25/embedding search) is directly relevant to qmd search backend tuning, since German compound words break exact matching (per the target's own qmd skill). The de-dupe-by-insertion-order trick (`list(dict.fromkeys(passages))`) is a nice small idiom. `[adopt]` for that one line as a Python idiom; `[adapt]` for the expansion strategy itself, tested offline first (P3/P4: by hand before automating).
4. **Two-stage retrieve-then-rerank pipeline** — cheap broad retrieval (Qdrant, k=20 per expanded query, ~80 pooled) followed by a second, more expensive re-ranking pass down to top 5-7 (`GeminiReranker`, `data_modules.py:72-98`). This is structurally the same shape as the target's own BM25-search-vs-reranked-query tradeoff (0.22s vs 2m41s) — cheap-cast-wide, then expensive-refine-narrow. `[catalogue]` — the two-stage shape is a good design pattern to name explicitly when benchmarking qmd backends, even though this repo's specific reranker (raw dot-product over Gemini embeddings) is unrelated to qmd's BM25/rerank choice.
5. **Reranker fails soft, not hard** — `GeminiReranker.forward` catches API exceptions and falls back to `passages[:k]` (unranked truncation) rather than crashing the whole query (`data_modules.py:95-97`). `[adopt]` as a general resilience pattern for any retrieval layer wired to a flaky backend/API — cheap and correctly named as a fallback, not a silent success.
6. **Centralized token-usage logging function** — `log_api_usage()` (`data_modules.py:16-23`), a single place all LM/embedding calls report through, printed with timestamp/provider/model/token counts. `[adopt]` — directly answers the target's stated open problem "cost/trace visibility of LM calls." The pattern (one function, call it from every site that touches `dspy.settings.lm.history[-1]`) is worth lifting even though the implementation here is just a print statement, not persisted anywhere.
7. **Try/except around `dspy.settings.lm.history[-1]['response'].usage`** — (`agents.py:27-31`, `52-56`) is the one concrete code snippet in this repo for reading DSPy's own call history to extract token counts after a module call. `[adopt]` as a literal recipe — it is the only working example of introspecting DSPy's LM history object here, worth copying verbatim (with the try/except, since it silently swallows the AttributeError if the response shape changes — that swallowing itself is a `[skip]`-worthy smell, log the exception).
8. **Conversational memory via history-condensation before intent classification** — `condense_question_with_history` (`main.py:113`, called `main.py:134-139`): a `ChainOfThought("chat_history, new_question -> standalone_question")` step runs *before* the orchestrator sees the question, so intent classification and retrieval always operate on a self-contained question. `[catalogue]` — not needed today (the target's `ask` step answers one question against static term pages, no chat history yet), but the pattern (normalize-before-classify) is the right place to put such a step if conversational `ask` is ever built.
9. **FastAPI global exception handler mapped to a specific upstream exception class** — `@app.exception_handler(LiteLLMRateLimitError)` (`main.py:38-50`) turns a third-party rate-limit exception into a structured 503 with a message, rather than a stack trace. `[adopt]` as a pattern for a future served `ask` endpoint if the target ever exposes wiki Q&A over HTTP — targeted exception-to-JSON handlers are cheap and legible.
10. **Startup-time model/pipeline construction, held once in app state** — `@app.on_event("startup")` builds the LM, retriever, reranker, and all three agents once and stores the orchestrator on `app.state.orchestrator` (`main.py:53-94`), rather than reconstructing per-request. `[adopt]` as an obvious-but-correct efficiency pattern for any served retrieval layer.
11. **Pydantic response model that always returns `context` alongside `answer` and `intent`** — `QueryResponse` (`main.py:107-110`) forces every response to carry the supporting passages, not just prose. `[adopt]` — directly aligned with P12 (quote, never paraphrase only): an API contract that structurally cannot omit its evidence is a good shape, even though *here* the evidence is unattributed dumped passage text, not per-line citations (see conflicts below).
12. **Vision-based OCR ingestion (Zerox) instead of naive text extraction** — `indexing.py:66-89` sends each PDF page as an image to a vision LLM to get structured Markdown (tables/layout preserved) rather than running a text-layer extractor. `[skip]` for kohaerenzprotokoll specifically — the target's `Sources/` are already Markdown from Drive exports, no PDF/OCR need — but `[catalogue]` as an idea if scanned-PDF sources ever enter the corpus.
13. **Recreate-collection-on-every-index-run for idempotency** — `qdrant_client.recreate_collection(...)` at the top of `indexing.py:58-64` avoids duplicate vectors on reruns by wiping first. `[skip]` — not applicable, the target has no vector index / no reindexing-by-truncation model (its "index" is `Wiki/index.json` derived deterministically), but noting the idiom for `[catalogue]`.
14. **Recursive character text splitter tuned to Markdown structure** — `separators=["\n\n", "\n", "##", "#", " "]`, `chunk_size=1024`, `chunk_overlap=150` (`indexing.py:94-98`). `[catalogue]` — a concrete, if unvalidated, starting parameter set if the target ever needs to chunk `Sources/drive/*.md` for embedding-based search; no evidence these numbers were tuned (they read as defaults), so treat as a guess, not a measurement (P24: done is a measurement — this isn't).
15. **`.gitignore` separates env/secrets, venvs by name, and Docker's persistent volume dir** (`.gitignore:1-4, 65-75`) — unremarkable but correctly done; nothing to adopt beyond confirming the target's own `.gitignore` discipline is already better (git-ignored `Plan/derived/`, venvs, etc., is the same idea already in place).
16. **Docstring-as-comment narration style throughout every file** (e.g. `data_modules.py:1-4`, `agents.py:1-3`) — every file opens with a plain-English paragraph of what it does and why, and most methods are commented step-by-step. `[catalogue]` as a documentation-convention data point: it makes a toy repo readable to a stranger fast, though it is prose-about-code, not the target's own convention of provenance-tagged claims (P2).
17. **ASCII pipeline diagram as a repo artifact** — `workflow.txt` is a full ASCII-art flow diagram of the FastAPI request lifecycle plus one worked example trace (condense → classify → expand → retrieve → rerank → generate) with concrete sample values at every step. `[adopt]` as a documentation *pattern*: a single worked example with real intermediate values, kept as a versioned file, is a good template for documenting the target's own account()/reconcile pipelines (which currently rely on prose description, not a worked numeric trace file).
18. **Metadata fields (`intent`) piggybacked onto the `dspy.Prediction` object post-hoc** — `prediction.intent = user_intent` (`agents.py:126`), read back via `getattr(prediction, 'intent', 'Unknown')` (`main.py:146`). `[skip]` — this is fragile (bolting an attribute onto a `dspy.Prediction` rather than declaring it in the signature's output fields); the target's own `account()` design (typed subject/question) is already better than this ad hoc mutation.
19. **Environment-variable presence checks before startup, fail loud** — `if not all([...]): raise ValueError(...)` in both `indexing.py:47-48` and `main.py:70-71`. `[adopt]` as a small, cheap pattern: refuse to start rather than fail deep in a call stack when a required config value is missing. Aligns loosely with P23 ("a guard reports what it could NOT check") though here it's presence-only, not correctness.
20. **`k` scaled by agent type** (`SimpleRAG` uses k=3, `ComparativeRAG` uses k=7, `agents.py:22,48`) — a small, concrete idea that different question *shapes* warrant different context-window sizes. `[catalogue]` — relevant if the target's `ask` step ever needs to decide how many term-page passages to pull in per question type (a single-term lookup vs. a "how do X and Y relate" question).

## 3. Directly reusable for the target

None of the code is directly reusable as-is — different retrieval substrate (Qdrant vector DB + OpenAI/Gemini embeddings vs. the target's `qmd` BM25/local index over Markdown; no API keys are meant to touch corpus text without a person's yes, per the target's Jev/TypeSafe gate), different DSPy API version (this repo predates or ignores DSPy 3.x's `dspy.Signature` classes; the target is pinned to DSPy 3.3.1 in `.venv-dspy`), and no test/fixture story to borrow (P5 requires an offline no-key fixture; this repo has zero offline path).

What maps loosely to the target's stated jobs:
- **Job "ask" (open, not yet built)**: the *shape* of `OrchestratorAgent` (classify → route to specialized responder) is the closest analog to an eventual intent-aware `ask` command that might need to distinguish "define this term" vs "compare these two terms" vs "trace this claim across documents." Would need: (a) the classifier's output typed and verified rather than string-contained; (b) every generated answer carrying `^[Lnn]` citations pulled from `Wiki/terms/*.md` by code, never typed by the model (P12/P26) — this repo's `context` field is just a list of raw passage strings with no line attribution, the opposite of what's needed.
- **qmd backend benchmarking (open problem)**: `QdrantRetrieverWithExpansion` and `GeminiReranker` are not usable (wrong stack, cost money, need Docker+3 keys), but the retrieve-then-rerank *two-stage measurement idea* is worth replicating structurally: measure recall of a cheap broad pass vs. precision/latency of a narrow reranked pass, exactly as the target already frames BM25 (0.22s) vs `query` (2m41s). The `Wiki/questions/*.md` fixture idea mentioned in the brief ("a search finds this in `<slug>`") is a much better gold set than anything in this repo, since this repo has none.
- **Multi-hop retrieval (open, none in target)**: `MultiStepRAG`'s decompose→answer-each→synthesize loop (`agents.py:62-90`) is the only concrete multi-hop code pattern found; if the target ever needs to answer a question spanning multiple wiki pages, this loop shape (not this code) is the reference to adapt, provided every sub-answer keeps its source line and the synthesis step is banned from inventing anything not present in the sub-answers (P13: never merge two sources' readings into one definition — this repo's synthesizer does exactly the forbidden merge, unmarked).
- **Cost/trace visibility (open problem)**: `log_api_usage()` (idea #6/#7 above) is the one piece worth lifting nearly verbatim as a starting point for instrumenting `.venv-dspy` calls, once the target starts making real model calls (jobs 1-4 in the brief).

Nothing here touches job 1 (one-term-or-two), job 2 (entity lists), or job 4 (skill-description optimization) at all.

## 4. Conflicts with the principles

- **P12/P26 (quote, never paraphrase; model never types a line number — code does)**: violated throughout. `SimpleRAG`/`ComparativeRAG`/`MultiStepRAG` all hand raw passage text to an LLM and accept freely generated prose as the "answer" (`agents.py:16,24,43,49,69,87`) with no citation mechanism at all — not even a document name, let alone a line number. The API's `context` field returns the passages used, but the answer text itself is not required to quote them or point back to them.
- **P13 (never merge two sources' readings into one definition; conflict detection is never mechanised)**: `MultiStepRAG.synthesizer` (`agents.py:69,87`) explicitly asks an LLM to merge multiple sub-answers into "a final, comprehensive answer" with no mechanism to preserve attribution or flag disagreement between sub-answers. This is the target's forbidden operation, done automatically and silently.
- **P1 (anything decidable is a program; judgement named as judgement)**: intent classification is decided by an unconstrained `dspy.Predict` and then read with a **fragile substring check** (`"Comparative" in user_intent`, `agents.py:115`) rather than a typed/enum output — a program pretending to make a deterministic decision on a genuinely free-text field, and not labeled as judgement anywhere.
- **P5 (every workflow ships an offline, no-key fixture)**: there is no offline path anywhere in this repo. Every module hard-requires OpenAI + Gemini + a running Qdrant Docker container; `indexing.py` and `main.py` both `raise ValueError` immediately if keys are absent, with no dry-run/stub mode.
- **P19 (assert non-empty + German)** and the target's German-only canon-prose rule: this repo has zero language handling — all prompts, signatures, and sample data (`workflow.txt`'s worked example) are English-only, over an English PDF (`documents/DBMS Notes.pdf`). No assertion anywhere checks output language or non-emptiness before use.
- **P24 (done is a measurement)**: the README claims "superior performance and intelligence" (`README.md:14`) and "high-quality knowledge base" (`README.md:16`) with zero benchmarks, evals, or measurements anywhere in the repo to back either claim — pure assertion, exactly the failure mode P24 exists to prevent.
- **Silent/unguarded cache-adjacent behavior**: `set(queries)` in `QdrantRetrieverWithExpansion.forward` (`data_modules.py:54`) silently drops duplicate rephrasings without logging what was deduped — a small instance of "quiet collapsing" the target's `quotes.py`/`state.py` culture explicitly argues against (measure and say, don't silently fold).
- **No test culture at all**: no `tests/`, no `selftest.py`-equivalent, no fixture proving any checker can fail — directly opposite the target's `selftest.py` philosophy ("nobody had ever seen any of them fail" is exactly the state of every code path here).
- **Broken packaging as shipped**: `src/agentic_rag/_init_.py` and `src/agentic_rag/components/__init__.py` — the top-level one is misnamed (single underscores) and both are empty; combined with no `requirements.txt`, the project as checked in cannot be `pip install -e .`'d and imported without a fix first. Worth naming as a trap: a demo repo's own README instructions do not reproduce a working install.

## 5. Dependencies & cost

- Targets **DSPy** at an unpinned, pre-3.x-style API (`dspy-ai` per README; uses `dspy.Retrieve` subclassing and bare-string signatures like `"context, question -> answer"`, which still work in 3.3.1 but the repo predates/ignores `dspy.Signature` classes and structured outputs). No version pin anywhere (no `requirements.txt`, no `pyproject.toml` version constraints) — genuinely unverified whether it runs unmodified against DSPy 3.3.1; (unverified) since it was never executed here.
- Heavy dependency surface: `dspy-ai`, `openai`, `qdrant-client`, `google-generativeai`, `numpy`, `fastapi`, `uvicorn`, `pydantic<2` (pinned below the target's likely pydantic version — a possible conflict if installed into a shared venv), `py-zerox`, `langchain`, `python-dotenv`.
- Requires: a running **Docker** container (Qdrant, `docker-compose.yml`), and three separate API keys/services — `OPENAI_API_KEY` (both generation and embeddings and Zerox OCR), `GEMINI_API_KEY` (reranking), plus `QDRANT_URL`/`QDRANT_COLLECTION_NAME`. None of these exist in the target's environment (`OPENROUTER_API_KEY`/`TYPESAFE_API_KEY` are the only keys the target names), and the target's own rule ("every call sends text to a third-party API, no corpus text goes through it until a person has decided it may") would block wiring German corpus text into Qdrant/OpenAI/Gemini without an explicit new decision.
- Could not be installed cheaply into a throwaway venv within the 2-minute/no-key budget given the Docker + 3-key requirement, so nothing was executed; all maturity claims above are from static reading, not a run. This is stated as such rather than inferred as working.
- `pydantic<2` pin is a real, concrete conflict risk if any of this code were ever vendored into a shared environment with the target's other tooling (dspytools needs Python 3.12, typesafe-sdk needs 3.11 — this repo's own README asks for Python 3.10, a fourth version, if it were ever run standalone).

## 6. Verdict

The single most valuable thing to take is the **classify-then-route orchestrator shape combined with the retrieve-then-rerank two-stage pattern** (items #1 and #4) — a legible template for a future `ask` command that needs to treat "define X" differently from "compare X and Y," and a reminder to measure a cheap-broad/expensive-narrow tradeoff explicitly rather than picking one qmd backend by guess. The centralized usage-logging function (#6/#7) and the worked-example diagram convention (#17) are small, cheap, worth lifting almost verbatim. Leave everything else: the Qdrant/OpenAI/Gemini stack, the unattributed-prose answers, the automatic multi-source synthesis, and the entire dependency/API-key footprint are all either irrelevant to the target's German-corpus/qmd substrate or directly forbidden by P12/P13 — this is a toy demo, never run, with no tests, broken packaging, and answers with no provenance at all.
